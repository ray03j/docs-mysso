## 1. テストレイヤー配分の代替パターン

テストピラミッド（単体テストが多い構造）は「基本」だが、プロジェクトの特性によっては他の配分が有効な場合もある。

### 1.1 アイスクリームコーン型（E2E 中心）

```
         /\
        /  \  単体テスト（少ない）
       /----\
      /      \  リクエストスペック（少ない）
     /--------\
    /          \  
   /------------\  統合テスト（中程度）
  /              \ 
 /                \ E2E テスト（多い）
/------------------\
```

**選定ポイント**

- レガシーシステムで単体テストが書きにくい（密結合・グローバル状態の塊）
- UI フローが複雑で、ユーザーの「操作感」が重要な Web アプリケーション
- リリース頻度が低く、テストの実行速度より「信頼性」を優先する
- テストチームと開発チームが分離しており、ブラックボックステストが主体

**トレードオフ**

| メリット | デメリット |
|---|---|
| 実際のユーザー操作に近いテストで安心感が高い | 実行が遅い（数分〜数十分） |
| ブラウザ間の互換性を確認できる | テストが壊れやすい（UI の変更で落ちる） |
| システム全体の連携を一度に確認できる | 失敗時の原因特定が困難（どのレイヤーが悪いか不明） |
| 開発者がテストを書く負担が少ない（テストチーム任せ） | フィードバックループが長く、開発速度が低下 |

**idp-user-service での適用可否**

- **推奨しない**。マイクロサービス内部の API エンドポイントとサービス層を E2E で覆うと、実行速度が許容できない。パスワードハッシュ化の単体テストを E2E に持ち込むと、テストの粒度が荒くなり、失敗時に「bcrypt の問題か、DB の問題か、HTTP 層の問題か」を判断できない。

### 1.2 ダイヤモンド型（統合テスト中心）

```
         /\
        /  \  E2E テスト（少ない）
       /----\
      /      \  単体テスト（少ない）
     /--------\
    /          \  
   /------------\  統合テスト（多い）
  /              \ 
 /                \ 
/------------------\
```

**選定ポイント**

- データベースや外部サービスとの「連携ロジック」がビジネス的核心
- 単体テストでは意味を持たない「DB クエリ最適化」や「トランザクション制御」が重要
- フレームワークの自動テスト機能（Rails の `system test`、Spring Boot の `@SpringBootTest`）が充実している
- チームが「統合テストで十分」との判断を持っている

**トレードオフ**

| メリット | デメリット |
|---|---|
| 実際の DB や外部サービスを使うため、モックの誤りを防げる | 実行速度が単体テストより遅い（DB アクセスが必要） |
| トランザクションや同時実行の問題を検出しやすい | テストデータの準備が複雑になり、テスト間の独立性が保ちにくい |
| フレームワークの挙動を含めて検証できる | ビジネスロジックの細かい分岐を網羅するコストが高い |
| 単体テストの設計コストが省ける | リファクタリング耐性が低い（DB スキーマ変更で大量のテストが壊れる） |

**idp-user-service での適用可否**

- **部分的に有効だが推奨しない**。サインアップ API → DB への永続化は統合テストで確認する必要があるが、bcrypt のハッシュ化ロジックやバリデーションの細かい分岐まで統合テストで覆うと、テストファイルが肥大化し、実行速度が低下する。統合テストは「リクエストスペック」で中程度に配置し、細かい分岐は単体テストに任せるのが現行の設計。

### 1.3 砂時計型（コントラクトテスト中心）

```
         /\
        /  \  E2E テスト（少ない）
       /----\
      /      \  統合テスト（少ない）
     /--------\
    /          \  
   /------------\  コントラクトテスト（中程度）
  /              \ 
 /                \ 単体テスト（多い）
/------------------\
```

**選定ポイント**

- マイクロサービス間の通信が多く、サービス間の「契約」が重要
- 各サービスが独立にデプロイされ、互いの開発サイクルが異なる
- 統合テストの環境構築が困難（サービスが多すぎて、全てを立ち上げるのが非現実的）
- Pact や Spring Cloud Contract などのコントラクトテストツールが導入されている

**トレードオフ**

| メリット | デメリット |
|---|---|
| サービスを単独でテストでき、開発サイクルを独立させられる | ツールの学習コストと導入コストがかかる |
| 統合テスト環境の構築コストを大幅に削減できる | コントラクトテストは「通信の形式」を検証するだけで「ビジネスロジックの正しさ」は保証しない |
| 消費者（Consumer）主導でテストを書くため、実際のニーズに即した契約が作れる | 実際のネットワーク障害やタイムアウトの検証は不十分 |
| サービス数が増えてもテスト実行時間が線形に増えない | ツールのバージョン管理や契約の管理が煩雑になる |

**idp-user-service での適用可否**

- **将来の拡張で有効**。現時点では `idp-user` と `idp-auth` の2サービスのみで、内部 API の数も少ないため、コントラクトテストツールの導入コストに見合わない。ただし、サービス数が増えた際（Phase 2 以降）は「`idp-auth` が `idp-user` に期待する JSON 構造」を Pact 等で管理することを検討すべき。現行のリクエストスペックは「手作りのコントラクトテスト」として機能している。

## 2. テスト作成タイミングの代替アプローチ

### 2.1 TDD（テスト先行開発）

**選定ポイント**

- ビジネスロジックが複雑で、実装前に「仕様」を明確にしたい
- チームが「テストを先に書く」ことの価値を理解し、実践できる
- レガシーコードの改修時に「既存の振る舞いを保証するテスト」を先に書く
- 開発者のスキルが高く、テストの設計に自信がある

**トレードオフ**

| メリット | デメリット |
|---|---|
| 実装前に「仕様の曖昧さ」を発見できる | 実装の方向性が不明確な探索的な作業では、テストを書くのが難しい |
| テストが実装の「使い方のドキュメント」になる | テスト先行のスキルがないチームでは、生産性が低下する |
| 過度な実装（YAGNI 違反）を防ぐ | 単純な CRUD では「テストを先に書く」オーバーヘッドが大きい |
| 設計がテストしやすい形（疎結合）に自然に導かれる | 期限が迫ったプロジェクトでは「テストを書く時間」を確保できない |

**idp-user-service での適用可否**

- **部分的に推奨**。`PasswordService` のような「純粋関数」や `AuthenticationService` のような「入出力が明確なサービス」は TDD に適している。テストを先に書くことで「空パスワードのガード」「bcrypt のプレフィックス確認」などの仕様が実装前に確定する。ただし、Rails のルーティング設定やコントローラーの骨組みは「フレームワークの慣習」であり、テストを先に書く価値は薄い。現行の設計では「サービス層は TDD、コントローラーは実装と並行してテスト」を推奨している。

### 2.2 テスト後追い（実装後にテスト）

**選定ポイント**

- プロトタイプや PoC（概念実証）で、まず「動くもの」を作りたい
- フレームワークの標準的な機能（Rails の Scaffold 等）を使い、独自のビジネスロジックが少ない
- チームのテスト文化が未成熟で、テスト先行は現実的でない
- 既存の実装に「後からテストを追加する」レガシー改修

**トレードオフ**

| メリット | デメリット |
|---|---|
| 実装の全体像を把握してからテストを書けるため、テストが無駄にならない | 実装のバイアスがテストに入り、「実装を確認するだけのテスト」になりがち |
| 探索的な実装に向いている | 実装が「テストしにくい構造」になってしまうことが多い |
| テストのスキルが低いチームでも開始しやすい | テストが後回しになり、最終的に「テストがないままリリース」になるリスク |
| 単純な機能では TDD のオーバーヘッドを回避できる | バグを実装時に発見できないため、後からの修正コストが高い |

**idp-user-service での適用可否**

- **現行アプローチとして採用している**。ブランチ計画ドキュメントでは「実装とテストを並行して書く」としており、厳密な TDD ではない。これは「サインアップ API」のような標準的な Rails 実装では、テスト先行の価値がサービス層より低いため。ただし、認証ロジックのようなセキュリティ関連の機能は「テストを先に書く」ことを推奨している。

### 2.3 テストなし（スパイク・プロトタイプ）

**選定ポイント**

- 技術的な不確実性が高く、「この技術選定が成立するか」を先に確認したい
- ワイヤーフレームや UI の動作確認が目的で、バックエンドの永続化は後回し
- 期限が極端に短く、一度きりのデモ用コード
- 投資対効果が不明確で、テストのコストを回収できない可能性がある

**トレードオフ**

| メリット | デメリット |
|---|---|
| 開発速度が最大になる | コードが「使い捨て」にならず、レガシーとして残るリスク |
| 技術的な実現可能性を素早く確認できる | バグが本番に潜り込み、後からの修正コストが爆発する |
| テストの設計コストをゼロにできる | 他の開発者がコードを読む・修正する際に「安全網」がない |
| 必要最小限のコードで検証できる | リファクタリングが恐くなり、コードが腐敗する速度が加速する |

**idp-user-service での適用可否**

- **適用しない**。認証・ユーザー管理はセキュリティの核心であり、「テストなしのスパイク」は許容できない。ただし、フロントエンドの「ログイン画面の UI フロー」など、idp-user-service とは独立した部分でスパイクを行うことはありえる。

## 3. テスト手法の代替アプローチ

### 3.1 プロパティベーステスト

**概要**

- 具体的な入力値を手動で定義するのではなく、「満たすべき性質（プロパティ）」を定義し、テストフレームワーク（RProp、fast-check 等）がランダムな入力を生成して検証する。
- 例：`PasswordService.verify?` のプロパティとして「正しいパスワードであれば必ず true を返す」「誤ったパスワードであれば必ず false を返す」を定義し、ランダムな文字列を数千回生成して確認する。

**選定ポイント**

- 入力の組み合わせが膨大で、手動で全ケースを列挙できない
- 数学的な性質（交換法則、結合法則、冪等性）を持つ関数
- バグの再現性が低く、「特定の入力でだけ落ちる」現象を検出したい
- 関数が純粋で、副作用がない

**トレードオフ**

| メリット | デメリット |
|---|---|
| 人間が思いつかないエッジケースを自動生成できる | テスト失敗時に「どの入力で落ちたか」をデバッグするのが難しい |
| テストコードの量が少なく、性質を記述するだけで済む | ランダム性のため、同じテストを実行しても「たまたま通る」ことがある（flaky） |
| 仕様の本質（プロパティ）を記述することで、実装に依存しないテストになる | プロパティの定義が難しく、逆に「実装を再現するだけのプロパティ」になりがち |
| 網羅的な入力網羅に近い検証ができる | 実行時間が例示テストより長い（数千回の試行） |

**idp-user-service での適用可否**

- **部分的に有効**。`PasswordService` の「ハッシュ化と検証の一貫性」はプロパティベーステストに適している。「任意の文字列をハッシュ化し、その文字列で検証すれば true を返す」というプロパティを定義できる。ただし、現行の設計では「例示テストで主要ケースを網羅」しており、プロパティベーステストの導入コストに見合わない。Phase 2 以降で「パスワードの複雑さルール」が追加された場合は検討価値がある。

### 3.2 スナップショットテスト

**概要**

- テスト実行時の出力（HTML、JSON、文字列）をファイルに保存し、次回実行時に「差分がないか」を比較する。
- 例：サインアップ API のレスポンス JSON を初回実行時に保存し、2回目以降は「同じ JSON が返るか」を確認する。

**選定ポイント**

- UI の HTML 構造や API の JSON レスポンスが「頻繁に変わる」が「意図的な変更かどうか」を確認したい
- 巨大な構造（複雑な JSON）を手動でアサーションするのが面倒
- フロントエンドのコンポーネントのレンダリング結果を確認したい
- 「現状の出力を保証する」ことが目的で、仕様の正しさは別途確認する

**トレードオフ**

| メリット | デメリット |
|---|---|
| 複雑な出力の検証を自動化できる | スナップショットの更新が「反射的」になり、「なぜ変わったか」を考えない |
| テストコードが非常に短くなる | 意図しない変更が「ただの差分」として埋もれ、レビューで見逃される |
| フロントエンドの DOM 構造変更を簡単に検出できる | 実装の詳細に過度に依存し、リファクタリングで大量のスナップショット更新が必要になる |
| 「現状の出力を記録」することで、回帰防止になる | テスト名が「スナップショット比較」だけで、何を保証しているかがわからない |

**idp-user-service での適用可否**

- **推奨しない**。API の JSON レスポンスは「フィールドの有無」「値の型」「セキュリティ上の制約（password_digest が含まれない）」を明示的に検証すべきであり、スナップショットテストでは「なぜこの JSON が正しいのか」が説明できない。ただし、フロントエンドの画面（feature/frontend-login）では「スナップショット + 明示的アサーション」のハイブリッドを検討できる。

### 3.3 コントラクトテスト（Pact 等）

**概要**

- マイクロサービス間の通信において、「消費者（Consumer）が期待するリクエスト・レスポンス」と「提供者（Provider）が実際に返すレスポンス」を個別にテストし、両者の「契約」を自動検証する。
- 例：`idp-auth`（Consumer）が `idp-user`（Provider）に `POST /api/v1/auth/verify` を期待する。`idp-auth` 側で「このリクエストを送ると、この JSON が返る」と定義し、`idp-user` 側で「このリクエストに対してこの JSON を返す」とテストする。両者を比較して契約が破壊されていないか確認する。

**選定ポイント**

- マイクロサービスが多く（10 個以上）、統合テスト環境の構築が非現実的
- 各サービスが独立の CI/CD パイプラインを持ち、互いにブロックしたくない
- 「契約の破壊」が本番事故の主要因になる
- チーム間の連携が「メールやドキュメント」で非公式に行われており、契約の管理が煩雑

**トレードオフ**

| メリット | デメリット |
|---|---|
| 統合テスト環境なしで、サービス間の整合性を確認できる | 導入コスト（Pact Broker の構築、CI 連携）が高い |
| 消費者主導でテストを書くため、使われない API を作らない | コントラクトテストは「形式の整合性」だけで「ビジネスロジックの正しさ」は保証しない |
| サービスを独立にデプロイでき、開発速度を維持できる | 学習曲線が急で、チーム全員の理解が必要 |
| 契約の変更が「破壊的かどうか」を自動判定できる | ツールのバージョン管理や、古い契約のクリーンアップが煩雑 |

**idp-user-service での適用可否**

- **現時点では「オーバーキル」、将来は「必須」**。現時点では `idp-user` と `idp-auth` の2サービスのみで、手動の「リクエストスペック」で十分。ただし、Phase 2 以降で `idp-client`、`idp-auth`、`idp-user` が複雑に連携するようになった場合、Pact の導入を検討すべき。現行のリクエストスペックは「手作りのコントラクトテスト」として機能している。

## 4. モック戦略の代替アプローチ

### 4.1 ロンドン学派（モック多用）

**概要**

- テスト対象の「周囲のオブジェクト」をすべてモック（スタブ）で置き換え、テスト対象だけを「完全に孤立」させてテストする。
- 例：`AuthenticationService.authenticate` をテストする際、`User.find_by` をモックして「戻り値を固定する」。DB には実際にアクセスしない。

**選定ポイント**

- テスト対象が「周囲のオブジェクトと密接に連携する」設計で、実際の連携をテストすると遅い・不安定
- 特定のメソッドが「呼ばれたかどうか」を検証したい（インタラクションテスト）
- テスト失敗時に「どのオブジェクトが原因か」を即座に特定したい
- チームが「単体テスト = クラス1つをテスト」という認識を持っている

**トレードオフ**

| メリット | デメリット |
|---|---|
| テストが非常に速い（DB や外部サービスにアクセスしない） | モックの実装が「実際の振る舞いと異なる」ことで、偽陽性（テストは通るが本番で壊れる）が生じる |
| テスト失敗時に「どのメソッドが呼ばれなかったか」を特定できる | テストが実装の詳細に過度に依存し、リファクタリングで大量に壊れる |
| 外部依存が未実装でもテストを書ける（ドライバー開発） | モックのセットアップコードが膨れ上がり、テストが読みにくくなる |
| 並列実行が容易（共有リソースを使わない） | 「本当に連携が取れているか」はテストしていないため、統合時に問題が発生する |

**idp-user-service での適用可否**

- **部分的に有効だが、現行では最小限**。`PasswordService` は `bcrypt` をラップするだけで、モックする必要はない（bcrypt は軽い）。`AuthenticationService` で `User.find_by` をモックすれば、テストは速くなるが、「DB のインデックスが効いているか」「クエリが正しいか」は検証できない。現行の設計では「DB を実際に使う」ことで、モックの偽陽性を避けている。ただし、外部サービス呼び出し（今後の拡張）ではモックが必要になる。

### 4.2 デトロイト学派（実装多用）

**概要**

- テスト対象と「その周囲の実際のオブジェクト」を使ってテストする。モックは「必要最小限」に留める。
- 例：`AuthenticationService.authenticate` をテストする際、実際の `User` モデルを DB に保存してからテストする。`PasswordService` も実際に使う。

**選定ポイント**

- 「実際の連携」が重要で、モックの偽陽性を許容できない
- テスト対象が「周囲のオブジェクトと疎結合」で、実際の連携をテストしても速い
- チームが「テスト = システムの振る舞いを保証する」という認識を持っている
- フレームワークが「テスト用 DB（SQLite インメモリ、test DB）」を軽量に提供している

**トレードオフ**

| メリット | デメリット |
|---|---|
| モックの偽陽性がなく、本番に近い挙動を検証できる | テストが遅くなる（DB アクセスや外部サービスのレイテンシが加わる） |
| リファクタリングに強い（実装の詳細に依存しない） | テストデータの準備が必要で、テストの記述が長くなる |
| 実際の連携問題をテストで発見できる | テスト間で状態が漏れるリスク（トランザクション管理が必要） |
| テストコードが「実際の使い方」を示すため、読みやすい | 外部依存が未実装の場合、テストを書けない（ブロッキング） |

**idp-user-service での適用可否**

- **現行アプローチとして採用している**。`User` モデルと `PasswordService` は実際に使い、DB も実際にアクセスする。これにより「bcrypt のハッシュが本当に保存されるか」「バリデーションが DB 制約と矛盾しないか」を検証できる。ただし、テストの実行速度を維持するため、テストトランザクションでロールバックし、テスト間の独立性を保っている。

## 5. テスト範囲の代替アプローチ

### 5.1 カバレッジ 100% 主義

**概要**

- コードカバレッジ（実行されたコード行の割合）を 100% を目指し、全ての分岐（if/else、case、例外）をテストで覆うことを強制する。

**選定ポイント**

- 安全_CRITICAL_なシステム（医療、航空、金融の核）で、バグが人命や法的責任に直結する
- 規制や監査で「テストカバレッジの証明」が義務付けられている
- チームが「テストを書く習慣」を定着させたい初期段階
- コードベースが小さく（数千行）、100% を達成することが現実的

**トレードオフ**

| メリット | デメリット |
|---|---|
| 未テストのコードが存在しないことを保証できる | カバレッジが高い ≠ テストが良い。「実装を再現するだけのテスト」でカバレッジを埋めることがある |
| チーム全体に「テストを書く」意識を植え付ける | 単純な getter/setter や定数定義までテストする必要があり、コストが大きい |
| 回帰テストの網羅性が高い | リファクタリング時に「テストを壊さずにカバレッジを維持する」負担が重い |
| 監査や規制対応で「テストの証拠」を提示できる | テストの品質（アサーションの厳密さ）が担保されない。カバレッジは「実行された」だけで「正しい結果を検証した」わけではない |

**idp-user-service での適用可否**

- **推奨しない**。Rails アプリケーションでは「フレームワークが生成するコード（migration、設定ファイル、Scaffold）」が多く、それらを 100% にする意味はない。現行の設計では「サービス層・モデル・コントローラーのビジネスロジック」を優先的にテストし、カバレッジは「副産物」として扱う。100% を目指すと、bcrypt の内部実装までテストする必要が出てきて、無駄なコストが生じる。

### 5.2 リスクベーステスト（現行アプローチ）

**概要**

- カバレッジの数値ではなく、「失敗した際の影響が大きい領域」を優先的にテストする。高リスク領域を厚く、低リスク領域を薄く（またはテストしない）する。

**選定ポイント**

- リソース（時間、人員）が有限で、すべてを等しくカバーできない
- システムの各部分で「失敗した際の影響」が大きく異なる
- ビジネス的に「セキュリティ」「データ整合性」が「UI の見た目」より重要
- チームが「テストの優先度」を判断できる知識を持っている

**トレードオフ**

| メリット | デメリット |
|---|---|
| 限られたリソースを最大効果で使える | 低リスク領域の「テストがない」という判断が、チームの合意を必要とする |
| 高リスク領域の信頼性を確保できる | リスクの評価が主観的になり、重要な部分を見落とす可能性がある |
| テストの実行速度を維持できる | 低リスク領域で「バグが発生した」際に「テストがない」という言い訳が生じる |
| チームの「どこが重要か」という認識を統一できる | リスク評価の基準がブレると、優先度の判断が曖昧になる |

**idp-user-service での適用**

- **現行アプローチとして採用している**。パスワード処理・認証ロジックを「高リスク」として厚くテストし、バリデーションエラーメッセージの日本語表記などは「低リスク」としてテストしない。これにより、テストの実行速度とメンテナンス性を維持しつつ、セキュリティの核心を保証している。

## 6. まとめ：選定の指針

以下のマトリクスは、idp-user-service のような「マイクロサービスの内部 API・認証系バックエンド」において、各代替アプローチを「採用する」「部分的に採用する」「推奨しない」に分類したもの。

| アプローチ | 採用 | 理由 |
|---|---|---|
| テストピラミッド（現行） | ✅ 推奨 | 単体テストでビジネスルールを網羅し、リクエストスペックで HTTP 契約を検証。実行速度と信頼性のバランスが最適 |
| アイスクリームコーン型 | ❌ 推奨しない | E2E 中心は実行速度が許容できず、マイクロサービスの内部 API では過剰 |
| ダイヤモンド型 | ⚠️ 部分的に | 統合テストは必要だが、細かい分岐は単体テストに任せるべき |
| 砂時計型（コントラクト） | ⚠️ 将来的に | 現時点では2サービスのみで過剰。Phase 2 以降で検討 |
| TDD | ⚠️ サービス層で | コントローラーは後追いでよいが、認証サービスは TDD が有効 |
| テスト後追い | ✅ 現行 | 標準的な Rails API は実装と並行してテストを書く |
| テストなし | ❌ 推奨しない | 認証系はセキュリティの核心であり、テストなしは許容できない |
| プロパティベーステスト | ⚠️ 将来的に | パスワードルールの複雑化時に検討価値あり |
| スナップショットテスト | ❌ 推奨しない | API の JSON 構造は明示的アサーションで検証すべき |
| コントラクトテスト | ⚠️ 将来的に | サービス数増加時に Pact 導入を検討 |
| ロンドン学派（モック多用） | ⚠️ 外部サービスで | 内部の DB アクセスは実際に使う。外部サービス呼び出しではモックを検討 |
| デトロイト学派（実装多用） | ✅ 現行 | DB や内部サービスは実際に使い、モックの偽陽性を防ぐ |
| カバレッジ 100% | ❌ 推奨しない | フレームワークコードまで含めると非現実的。重要なビジネスロジックを優先 |
| リスクベーステスト | ✅ 現行 | セキュリティ・データ整合性を優先し、エラーメッセージの i18n などは後回し |

**最終的な判断基準**

- **「このテストが失敗したら、どういう本番事故が起こるか」を想像する**
- **「このテストが通っても、本番で壊れる可能性があるか」を疑う**
- **「このテストのメンテナンスコストは、得られる価値を上回るか」を問う**

現行の設計は「これらの問いに対して、idp-user-service の文脈で最もバランスの取れた答え」として選択している。プロジェクトの規模やフェーズが変われば、答えも変わることを認識しておく必要がある。
