# TDD を「動いたから OK」型の人がどう信頼するか

## 結論

TDD は「動いたから OK」という感覚を**手動確認から自動証明に移行させる**仕組みです。「動かないものを盲信する」のではなく、「動く前の状態を確認する品質管理」です。

---

## 1. TDD は「動いたから OK」型の人にこそ効果的

### 「動いたから OK」派の陥りやすい罠

| 問題 | 原因 | 結果 |
|------|------|------|
| 「動く」定義が曖昧 | 手動確認で満足 | エッジケースを見落とす |
| 後で壊れても気づけない | 自動検証がない | 修正が他を破壊していても知らない |
| リファクタリングが怖い | 動作保証がない | 技術負債が蓄積する |

### TDD がもたらす具体的な信頼

- **「壊れたらすぐ分かる」**: 修正のたびに全テスト実行で影響範囲を検知
- **「動作の定義がコードとして残る」**: 3 ヶ月後の自分が「何が正しい動作か」を確認できる
- **「小さな安心の積み重ね」**: 1 つのテスト ≈ 1 つの約束事が履行された証明

---

## 2. なぜ「動かない」状態で信頼できるか

TDD は「動く」までの過程を設計する手法です。

### TDD の 3 フェーズ

| フェーズ | 状態 | 信頼の根拠 |
|---------|------|-----------|
| **赤 (Red)** | テストが失敗する | 「この要件が満たされていない」という事実が自動化される |
| **緑 (Green)** | テストが通る | テストが通る = 要件が満たされているという証明 |
| **青 (Refactor)** | テストが通るまま構造を改善 | 動作を保証したまま構造を改善できる |

---

## 3. 「失敗するテスト」をどう信頼するか

### 重要な誤解を解く

> 「失敗するテストを信頼する」 ≠ 「動かないものを盲信する」

**「失敗するテストを信頼する」= 「失敗するはずのテストが、正しく失敗することを確認してから信頼する」**

### 実際の流れ

```
1. テストを書く
2. 実行して失敗する
3. 失敗の理由を確認する ← ここが重要
4. 理由が正しければ実装に進む
```

### 失敗の確認ポイント

| 確認項目 | 期待される失敗 | 信頼の根拠 |
|---------|-------------|-----------|
| **エラーメッセージ** | `expected X but got Y` | テストが正しい対象を検証している |
| **失敗の場所** | 実装がない部分 | テストが実装を呼んでいる |
| **失敗の形** | 型エラー、null エラー、未定義 | 実装が未完了であることを証明 |

### 失敗パターンと判断

| 失敗のパターン | 判断 | 次のアクション |
|-------------|------|------------|
| `function not found` | 正しい失敗 | 実装を書く |
| `assertion failed: expected 3 but got 0` | 正しい失敗 | 実装を書く |
| `SyntaxError` | テストが壊れている | テストを修正する |
| `ModuleNotFoundError` | インポート間違い | テストを修正する |
| テストが通る | 実装が既に存在 or テストが無意味 | 確認する |

### 具体例

```python
# テストを書いた
assert add(1, 2) == 3

# 実行結果
# NameError: name 'add' is not defined
# → これを見て「あ、正しい失敗だ」と確認
```

**確認がないと**: テストが実際は壊れていても気づかず、実装後に「なぜかテストが通らない」という状態になります。

---

## 4. まとめ

1. **「失敗するテストを書く」は一連の作業**: 書いて、実行して、**確認して**初めて次に進む
2. **「正しく失敗した」ことを確認**: これにより「テストが動作すること」「テストが検証したい対象を正しく指していること」の両方が担保される
3. **段階的な信頼の構築**: 赤 → 緑 → 青の各段階で、小さな証明を積み重ねていく

TDD は「動かないものを信じる」技術ではなく、「**動くことを機械的に証明する仕組み**」です。最初はテストを書くのが面倒に感じますが、一度「修正しても即座に壊れを検知する」体験をすると、その安心感が手放せなくなります。
