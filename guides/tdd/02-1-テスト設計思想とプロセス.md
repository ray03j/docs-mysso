## 1. テスト設計の基本思想

テスト設計とは「動作を証明するための文章を設計する」作業である。コードが書かれた後に「テストを付ける」のではなく、実装前に「この機能が正しいと言えるためには何を保証する必要があるか」を構造化して定義する。

### 1.1 テストピラミッド

テストの設計・配置は以下のピラミッドに従う。上に行くほど実行コストが高く、下に行くほど実行速度が速くフィードバックが得られる。

```
           /\
          /  \  E2E / 統合テスト（少ない）
         /----\     ・マイクロサービス間連携
        /      \    ・エンドツーエンドの認証フロー
       /--------\   ・実行は遅い、壊れやすい、信頼度高い
      /          \  
     /------------\ リクエストスペック（中程度）
    /              \   ・API エンドポイントの入出力
   /                \  ・HTTP ステータス・ヘッダー・JSON 構造
  /------------------\ ・ルーティング・ミドルウェアの検証
 /                    \ 
/----------------------\ 単体テスト（多い）
                          ・モデルバリデーション
                          ・サービス層の純粋関数
                          ・ビジネスルールの網羅
                          ・実行は速い、安定、メンテナンス容易
```

**なぜこの構造か**

- **単体テストを多くする理由**：サービス層の `PasswordService` のような純粋関数は、入力と出力だけで完結する。テストは数ミリ秒で終わり、外部依存がないため揺らぎがない。ビジネスルールの網羅はここで行う。
- **リクエストスペックを中程度にする理由**：コントローラーは「ルーティング + パラメータ解析 + サービス呼び出し + レスポンス整形」を行う。すべての分岐を網羅する必要はなく、各エンドポイントの「成功・主要な失敗・エラーレスポンス」を確認する。
- **E2E / 統合テストを少なくする理由**：マイクロサービス間の連携は環境構築が重い。テストが落ちた際に「どのサービスが原因か」を切り分けにくい。信頼性は高いが、コストも高いため、最小限に留める。

### 1.2 レイヤー別の責務とテスト方針

| レイヤー | 責務 | テストで保証すべきこと | テスト種別 |
|---|---|---|---|
| **モデル** | データの整合性、バリデーション、コールバック | 制約違反を防ぐ、コールバックが正しく動作する | 単体テスト（model spec） |
| **サービス** | ビジネスロジック、外部ライブラリのラップ | 純粋関数の入出力、境界値、異常系 | 単体テスト（service spec） |
| **コントローラー** | リクエスト受信、パラメータ処理、レスポンス返却 | HTTP ステータス、JSON 構造、エラーハンドリング | リクエストスペック |
| **ルーティング** | URL → コントローラーアクションの対応 | エンドポイントが正しく解決される | リクエストスペック（暗黙的） |

**なぜこの対応か**

- **モデルは「データの守護者」**：DB 制約とバリデーションが最後の防波堤。ここが緩いと不正なデータが永続化される。
- **サービスは「ビジネスルールの実装者」**：コントローラーが「どう呼び出すか」を知るなら、サービスは「何を計算するか」を知る。テストは計算結果を検証する。
- **コントローラーは「インターフェースの実現者」**：HTTP という外部プロトコルを内部処理に橋渡しする。テストはプロトコルレベルの契約を検証する。

### 1.3 マイクロサービス特有の考慮

マイクロサービスアーキテクチャでは、テスト設計に以下の追加観点が必要になる。

**内部 API としての契約**

- `idp-user` は `idp-auth` から呼び出される内部サービス。レスポンスの JSON 構造・フィールド名・ステータスコードは「契約」である。変更は呼び出し側に破壊的影響を与える。
- テストでは「レスポンスに含まれるフィールド」と「含まれないフィールド」を両方検証する。例：`password_digest` がレスポンスに含まれないことを確認する。

**ステートレス性の保証**

- `idp-user` はステートレスな API サービス。セッション管理は `idp-auth` で行う。テストでは「単一リクエストで完結する」を確認し、リクエスト間の状態汚染がないことを保証する。

**タイミング攻撃のリスク意識**

- 認証系 API は「存在しないメール」と「パスワードが違う」場合で処理時間に差が出ないようにする。テストでは両方を区別せずに同じレスポンスを返すことを確認する。

### 1.4 テスト設計の核心：「何を保証したいか」から始める

テスト設計の最初の問いは「このコードが正しく動作していると言えるためには、どういう証拠が必要か」である。

```
【誤りの順序】
コードを書く → テストを書く → 「テストが通る」ことを確認する

【正しい順序】
「この機能の正しさとは何か」を定義する → テストケースを設計する → コードを書く → テストが通ることを確認する
```

テストケースは「仕様の実行可能な文書」である。テストが通ることと「実装が正しいこと」は同義ではない。テストケース自体が「正しい問い」を投げかけているかが重要。

## 2. テスト設計プロセス（7ステップ）

以下のプロセスは `idp-user-service` に限らず、任意の機能・サービスに適用できる。

### Step 1: 境界とインターフェースの定義

**実施内容**

1. テスト対象の「入力」と「出力」を明確にする
2. 外部に公開するインターフェース（メソッド署名、API エンドポイント、パラメータ構造）を列挙する
3. 依存する外部リソース（DB、他サービス、ライブラリ）を特定する

**具体例：サインアップ API**

- **入力**：`POST /api/v1/users`、JSON ボディ `{ user: { email, password, name } }`
- **出力**：`201 Created` + `{ id, email, name }`、または `422 Unprocessable Entity` + `{ errors: [...] }`
- **外部依存**：PostgreSQL（User テーブル）、bcrypt（ハッシュ化）

**設計ポイント**

- 入力は「パラメータ構造」と「データ型」と「必須/任意」を定義する。Strong Parameters の許可リストと対応させる。
- 出力は「HTTP ステータス」と「レスポンスボディ構造」と「含まれないフィールド」を定義する。
- 外部依存は「テストでモックするか、実際に使うか」をここで決定する。bcrypt は実際に実行しても軽いためモック不要。DB はテスト用に実際に使う（テストトランザクションでロールバック）。

#### なぜこのステップが最初か

- **ブラックボックス思考の確立**：実装の詳細に引きずられる前に「この機能が外部に何を約束するか」を定義することで、テストと実装の両方が同じ契約に基づいて作られる。これにより「実装が変わっても振る舞いは変わらない」という安定したテストが書ける。
- **スコープの明確化**：境界を定義しないと、テストが「内部のプライベートメソッド」や「無関係な外部サービス」まで蔓延し、メンテナンスコストが爆発する。入力・出力を狭めて定義することで、テスト対象を絞り込む。
- **モックの判断基準**：外部依存を先に列挙することで、「何を実際に動かし、何をモックするか」を計画的に決定できる。bcrypt のように「軽くて信頼性が高い」ライブラリはモックせず実際に使うことで、モックの実装ミスによる偽陽性を防ぐ。

### Step 2: リスクと優先度の評価

**実施内容**

1. 各機能に対して「失敗した際の影響」を評価する
2. 影響が大きい順にテストの優先度を設定する
3. 「必ずテストする」領域と「カバレッジが低くても許容する」領域を分ける

**評価基準（汎用）**

| リスク項目 | 高リスク（優先度：高） | 低リスク（優先度：低） |
|---|---|---|
| **セキュリティ** | 認証・認可、パスワード処理、個人情報 | 公開情報の表示順 |
| **データ整合性** | 書き込み・更新・削除 | 読み取り一覧 |
| **金銭/法的** | 課金、契約、監査ログ | 開発環境のみの機能 |
| **可用性** | コアフローの障害 | エッジケースでのフォールバック |

**idp-user-service の適用**

- **高優先度**：パスワードが平文保存されないこと、bcrypt ハッシュ化が正しく動作すること、認証失敗時にセーフなレスポンスを返すこと
- **中優先度**：サインアップ時のバリデーションエラーメッセージ構造
- **低優先度**：エラーメッセージの日本語/英語表記（現時点では i18n 未導入）

#### なぜ優先度をつけるか

- **リソースの最適配分**：すべての機能を等しくテストすると、実行時間・メンテナンスコストが爆発する。実際に「すべての分岐を網羅的にテストする」ことは現実的でない。優先度をつけることで、限られたリソースを「失敗したときの影響が大きい領域」に集中させる。
- **早期の重大バグ防止**：セキュリティやデータ整合性のテストを先に実施することで、コア機能の信頼性を確保してから周辺機能を整える。これにより、後から「設計の根本を見直す」という無駄を減らせる。
- **低優先度の明示的な許容**：「テストしない」という判断を文書化することで、チーム内で「なぜここはテストが薄いのか」を共有できる。技術的負債として管理し、必要に応じて後から追加する判断材料になる。

### Step 3: テストレイヤーの割り当て

**実施内容**

1. 各機能を「モデル」「サービス」「コントローラー」のどのレイヤーでテストするか決定する
2. 同じ分岐を「複数レイヤーで重複テストしない」ように調整する
3. 各レイヤーで「他のレイヤーの挙動を前提とする」形でテストを簡潔にする

**割り当ての原則**

- **ビジネスルールの分岐** → サービス層の単体テストで網羅する
- **HTTP 契約の検証** → コントローラーのリクエストスペックで網羅する
- **データ整合性の検証** → モデルの単体テストで網羅する

**重複を避ける例**

- `PasswordService.verify?` の「空文字列で false を返す」テストはサービス層で実施する。
- コントローラーのテストでは「空パスワードで 401 が返る」だけを確認し、サービス層の内部動作までは検証しない。
- これにより、サービス層の実装を変更しても、コントローラーのテストは壊れにくくなる（疎結合）。

#### なぜ重複を避けるか

- **テストの安定性向上**：同じ分岐を複数レイヤーでテストすると、実装の無関係な変更（リファクタリング）で複数のテストが同時に壊れる。これは「壊れやすいテスト（fragile test）」を生み出し、開発者が「テストを直す」ことに時間を取られ、テストへの信頼が低下する。
- **責務の明確化**：各レイヤーが「自分の責務だけを保証する」ことで、テスト失敗時に「どのレイヤーに問題があるか」を即座に特定できる。サービス層のテストが落ちたらビジネスロジックを、コントローラーのテストが落ちたら HTTP 契約を調べればよい。
- **テストの速度維持**：リクエストスペックは DB アクセスや Rack スタックの実行を伴うため、サービス層の細かい分岐まで網羅すると実行時間が数倍に膨れる。サービス層の単体テストで網羅することで、フィードバックループを短く保つ。

### Step 4: 境界値・異常系の洗い出し

**実施内容**

1. 「正常系」だけでなく「境界値」「異常系」を体系的に列挙する
2. 以下の観点を順に適用する

**観点チェックリスト**

| 観点 | 問い | 例 |
|---|---|---|
| **空・未入力** | 空文字、nil、未送信の場合はどうなるか | `email: ''`、`password: nil` |
| **最大・最小値** | 長さ制限の境界はどうなるか | `name` が 100 文字ちょうど、101 文字 |
| **重複・一意性** | 一意制約に違反する場合はどうなるか | 既存メールでサインアップ |
| **型の違反** | 期待する型と異なる場合はどうなるか | 数値を文字列フィールドに送信 |
| **認可・認証** | 未認証でアクセスできないか | 今後の拡張で必要になる可能性 |
| **セキュリティ** | 機密情報が漏洩しないか | `password_digest` がレスポンスに含まれない |
| **外部依存障害** | DB 接続失敗、外部サービスダウン時はどうなるか | トランザクション処理の確認 |

**idp-user-service の適用**

| 観点 | 正常系 | 境界値/異常系 |
|---|---|---|
| email | 有効なメール | 空、nil、重複 |
| password | 有効な平文 | 空、nil、短い文字列 |
| name | 有効な名前 | 101 文字（上限超過） |
| ハッシュ化 | 正しく保存される | 平文が保存されない |
| レスポンス | 201 + ユーザ情報 | 422 + エラーメッセージ、401 + `authenticated: false` |

#### なぜ正常系だけではダメか

- **バグは境界に潜む**：コードの分岐点（`if` 文、バリデーション、ガード節）は、正常系だけでは評価されない。空文字や `nil` が渡された場合の挙動、配列の最初と最後の要素、整数の最大値・最小値など、境界値でこそバグが顕在化する。
- **ユーザーの入力は常に想定外**：実際の運用では「想定外の入力」が必ず発生する。フロントエンドのバリデーションをすり抜けたり、API を直接叩く悪意あるリクエストや、単純な操作ミスで異常な値が送信される。異常系をテストしないことは「想定外を想定しない」ことであり、システムの脆弱性を残す。
- **体系的な洗い出しで漏れを防ぐ**：「あとで思いついた異常系を追加する」アプローチでは、人的な記憶に依存し漏れが生じる。観点チェックリスト（空・最大最小・重複・型・セキュリティ）を順に適用することで、忘れやすいエッジケースを機械的に網羅できる。

### Step 5: テストケースの具体化

**実施内容**

1. Step 4 で洗い出したケースを「テストケース記述」に変換する
2. 各テストケースは「前提条件（Given）・操作（When）・期待結果（Then）」の構造を持つ
3. テスト名は「何を・どういう条件で・どうなるか」を表現する

**テストケース記述のテンプレート**

```
【テスト名】[条件] の場合、[結果] となる

- Given: [前提条件]
- When: [操作・入力]
- Then: [期待結果]
```

**具体例：サインアップ API**

```
【テスト名】有効なパラメータの場合、ユーザーを作成する

- Given: データベースに該当メールのユーザーが存在しない
- When: POST /api/v1/users に { user: { email: "a@b.com", password: "pass123", name: "Test" } } を送信
- Then: User テーブルのレコード数が 1 増加し、201 Created が返る

【テスト名】重複したメールアドレスの場合、ユーザーを作成しない

- Given: データベースに email: "a@b.com" のユーザーが存在する
- When: 同じメールでサインアップを送信
- Then: レコード数が変化せず、422 Unprocessable Entity が返る
```

#### なぜ Given-When-Then か

- **仕様文書としての機能**：テストケースを「前提・操作・結果」に分離することで、プログラミングの専門知識がなくても読める仕様文書になる。プロダクトオーナーや QA、新しい開発者がテストを読むことで「この機能が何を約束しているか」を理解できる。
- **思考の分離**：前提条件と操作と結果を混ぜて書くと、テストの意図が曖昧になり「どの条件が結果に影響したのか」を判断しにくくなる。GWT は各要素を分離することで、テストの「なぜ」を明確にする。
- **失敗時の即座の原因特定**：テストが失敗した際に「Given が整っていない」「When の操作が違う」「Then の期待が間違い」という3つのどこに問題があるかを即座に切り分けられる。これによりデバッグ時間を短縮する。

#### なぜテスト名に「条件と結果」を含めるか

- **テスト失敗時の可読性**：`test user` のような曖昧な名前では、テストが落ちた際に「何が壊れたのか」をログを読み込むまで判断できない。`有効なパラメータの場合、ユーザーを作成する` という名前なら、失敗通知を見ただけで「サインアップの正常系が動かない」と理解できる。
- **仕様の網羅性確認**：テスト名を一覧で見ただけで「この機能のどういう条件が網羅されているか」が把握できる。テスト名が条件を含まないと、同じ条件を重複してテストしたり、逆に重要な条件を漏れたりする。
- **レビュー時の理解コスト削減**：コードレビューでテスト名だけを見て「この機能は何を保証しているか」を判断できる。テストの中身を読まなくても仕様の妥当性を評価できるため、レビュー効率が上がる。

### Step 6: テストデータとファクトリ設計

**実施内容**

1. テストで使用するデータを「ファクトリ」または「フィクスチャ」として定義する
2. 一意制約があるフィールドは `sequence` を使う
3. テスト間でデータが汚染しないことを保証する

**ファクトリ設計の原則**

- **最小データ原則**：テストに必要な最小限の属性だけを定義する。余計な属性を入れると、モデル変更時に無関係なテストが壊れる。
- **一意性の自動生成**：`email` など一意制約のあるフィールドは `sequence` で自動生成する。これにより「複数のテストで `create(:user)` を呼んでも衝突しない」を保証する。
- **関連データのトレイト**：特定の状態を持つデータ（管理者、無効ユーザーなど）は FactoryBot の `trait` を使って定義する。

**idp-user-service のファクトリ設計例**

```ruby
FactoryBot.define do
  factory :user do
    sequence(:email) { |n| "user#{n}@example.com" }
    password { 'password123' }  # 仮想属性
    name { 'Test User' }

    trait :invalid do
      email { '' }
      password { '' }
    end
  end
end
```

#### なぜ最小データ原則か

- **テストの意図の明確化**：テストデータに「このテストには不要な属性」を含めると、読み手が「この属性はテストの結果に影響するのか」と判断する必要が生じる。最小データにすることで、テストが「何を検証しているか」を即座に理解できる。
- **壊れやすいテストの防止**：モデルに新しい必須バリデーションが追加された際に、無関係なテストのファクトリが壊れることを防ぐ。例えば「電話番号」が必須になった場合、サインアップ API のテストに電話番号が不要なら、テストは壊れない。
- **テストの独立性確保**：テストデータが複雑になると、テスト間で「どのデータがどこで使われているか」を追跡するのが難しくなる。最小データであれば、各テストが「自分のデータだけを管理する」という独立性を保ちやすい。

#### なぜ sequence で一意性を自動生成するか

- **テスト間の衝突防止**：一意制約があるフィールド（`email`）を固定値で定義すると、複数のテストで `create(:user)` を呼んだ際に「同じメールで重複」してテストが失敗する。`sequence` は実行順序に依存して自動的に異なる値を生成するため、テストの並列実行やランダム実行にも安全である。
- **明示的なデータ指定の許容**：`sequence` を使っても、`create(:user, email: 'fixed@example.com')` のように特定のテストで明示的に値を上書きできる。これにより「柔軟性」と「安全性」の両方を得られる。
- **人間の負担軽減**：テスト作成者が「衝突しないメールを考える」という認知負荷を減らす。特にテストの数が増えた際に、人間が一意な値を管理するのは非現実的である。

### Step 7: 実装・実行・フィードバック

**実施内容**

1. テストを実装する（先にテストを書くか、実装と並行して書く）
2. テストを実行し、すべて通ることを確認する
3. テストが壊れやすい箇所（壊れる原因が実装の無関係な変更にある）を特定し、リファクタリングする

**実行の順序**

```bash
# 1. モデルテスト（最速、最も安定）
bundle exec rspec spec/models/user_spec.rb

# 2. サービステスト
bundle exec rspec spec/services/user/

# 3. リクエストスペック（API 契約）
bundle exec rspec spec/requests/

# 4. 全体（CI 用）
bundle exec rspec
```

**フィードバックの観点**

- テストが「実装の詳細」に依存していないか（例：サービスの内部メソッド名を直接検証していないか）
- テスト名だけで「何を保証しているか」がわかるか
- テスト失敗時のエラーメッセージが「何が違ったか」を示しているか

#### なぜこの実行順序か

- **失敗の切り分けが容易**：単体テストから順に実行することで、テストが失敗した際に「問題はビジネスロジックか、HTTP 層か、統合か」を即座に特定できる。リクエストスペックから実行した場合、失敗の原因が「コントローラーのバグなのかサービス層のバグなのか」判断に時間がかかる。
- **フィードバック速度の最適化**：単体テストは数ミリ秒で終わる。サービス層のテストを先に実行して通ることを確認してから、リクエストスペックを実行する。これにより「コントローラーの問題かサービス層の問題か」を素早く切り分けられる。開発者の「待ち時間」を最小化し、集中力を維持する。
- **CI とローカルの使い分け**：ローカル開発では「失敗したテストだけを再実行」し、CI では「すべてのテストを実行する」という使い分けが自然になる。単体テストが通っている状態でリクエストスペックを実行すれば、調査対象を絞り込める。

#### なぜフィードバックループを回すか

- **テスト自体の品質向上**：テストが「実装の詳細」に依存していると、無関係なリファクタリングでテストが壊れる。これにより開発者が「テストを直す」という非生産的な作業に時間を取られ、テストへの信頼が失われる。フィードバックループで「壊れやすいテスト」を特定し、修正することで、テストスイート全体の価値を維持する。
- **テスト名の品質確認**：テスト名だけで「何を保証しているか」がわからない場合、そのテストは「仕様文書としての機能」を失っている。テスト失敗時のエラーメッセージが「何が違ったか」を示していない場合、開発者はテストの中身を読み解く時間を浪費する。フィードバックでこれらを定期的に見直すことで、テストの「自己説明性」を保つ。

## 3. idp-user-service への適用例

本プロセスを `feature/idp-user-service` の各ブランチに適用した結果を示す。

### 3.1 サインアップ API（UsersController）

**Step 1: 境界定義**

- 入力：`POST /api/v1/users`、`{ user: { email, password, name } }`
- 出力：`201 Created` + `{ id, email, name }` または `422` + `{ errors: [...] }`

**Step 2: リスク評価**

- 高：パスワードが平文保存されない、重複メールでデータが汚染されない
- 中：バリデーションエラーメッセージの構造

**Step 3: レイヤー割り当て**

- モデル：バリデーション、`has_secure_password` によるハッシュ化
- コントローラー：Strong Parameters、HTTP ステータス、レスポンス構造
- サービス：ハッシュ化処理は `PasswordService` に委譲（コントローラーでは検証しない）

**Step 4: 境界値・異常系**

| 観点 | ケース |
|---|---|
| 空・未入力 | `email: ''`、`password: ''` |
| 最大値 | `name` が 100 文字ちょうど、101 文字 |
| 重複 | 既存メールでサインアップ |
| セキュリティ | `password_digest` がレスポンスに含まれない |

**Step 5: テストケース**

| テスト名 | レイヤー |
|---|---|
| 有効なパラメータの場合、ユーザーを作成する | リクエストスペック |
| 有効なパラメータの場合、201 Created を返す | リクエストスペック |
| 有効なパラメータの場合、password_digest が bcrypt で保存される | リクエストスペック |
| 無効なパラメータの場合、ユーザーを作成しない | リクエストスペック |
| 無効なパラメータの場合、422 を返す | リクエストスペック |
| 重複メールの場合、ユーザーを作成しない | リクエストスペック |
| email が必須である | モデルスペック |
| password が present の場合、保存時にハッシュ化される | モデルスペック |

### 3.2 認証サービス層（PasswordService / AuthenticationService）

**Step 1: 境界定義**

- `PasswordService.hash(password)` → bcrypt ハッシュ文字列
- `PasswordService.verify?(password, password_digest)` → true/false
- `AuthenticationService.authenticate(email, password)` → User または nil

**Step 2: リスク評価**

- 高：パスワード検証の誤り（認証バイパス）、bcrypt の誤用
- 中：タイミング攻撃（Phase 2 で厳密対応）

**Step 3: レイヤー割り当て**

- サービス層のみで網羅。コントローラーは「認証成功・失敗の分岐」だけを確認する。

**Step 4: 境界値・異常系**

| 観点 | ケース |
|---|---|
| 空 | `password: ''`、`password_digest: ''` |
| 誤り | 正しいハッシュに誤ったパスワード |
| 存在 | 存在しないメールで認証 |
| ソルト | 同じ平文で異なるハッシュが生成される |

**Step 5: テストケース**

| テスト名 | レイヤー |
|---|---|
| 正しいパスワードで true を返す | サービススペック |
| 誤ったパスワードで false を返す | サービススペック |
| 空のパスワードで false を返す | サービススペック |
| 空のハッシュで false を返す | サービススペック |
| 同じ平文でも異なるハッシュを生成する | サービススペック |
| 正しいメール・パスワードでユーザーを返す | サービススペック |
| 存在しないメールで nil を返す | サービススペック |

### 3.3 ログイン検証 API（VerifyController）

**Step 1: 境界定義**

- 入力：`POST /api/v1/auth/verify`、`{ email, password }`（フラット構造）
- 出力：`200 OK` + `{ authenticated: true, user: { id, email, name } }` または `401` + `{ authenticated: false }`

**Step 2: リスク評価**

- 高：`password_digest` がレスポンスに含まれない
- 高：「存在しないメール」と「誤ったパスワード」を区別しない
- 中：HTTP 401 の適切な使用

**Step 3: レイヤー割り当て**

- コントローラー：HTTP ステータス、レスポンス構造、認証結果の分岐
- サービス：認証ロジック（テスト済みの `AuthenticationService` を前提とする）

**Step 4: 境界値・異常系**

| 観点 | ケース |
|---|---|
| 成功 | 正しいメール・パスワード |
| 失敗（誤り） | 正しいメール・誤ったパスワード |
| 失敗（不存在） | 存在しないメール |
| セキュリティ | `password_digest` がレスポンスに含まれない |

**Step 5: テストケース**

| テスト名 | レイヤー |
|---|---|
| 正しい認証情報の場合、authenticated: true を返す | リクエストスペック |
| 正しい認証情報の場合、200 OK を返す | リクエストスペック |
| 正しい認証情報の場合、ユーザー情報を返す（password_digest 除く） | リクエストスペック |
| 誤ったパスワードの場合、authenticated: false を返す | リクエストスペック |
| 誤ったパスワードの場合、401 Unauthorized を返す | リクエストスペック |
| 存在しないメールの場合、authenticated: false を返す | リクエストスペック |
| 存在しないメールの場合、401 Unauthorized を返す | リクエストスペック |

## 4. 汎用チェックリスト

以下は任意の API 機能・サービス層に適用できるチェックリスト。テスト設計完了後、各項目を確認する。

### 4.1 単体テスト（モデル・サービス）

- [ ] 正常系の入力で期待される出力が得られる
- [ ] 空・nil の入力で適切なガードまたはエラーが発生する
- [ ] 最大値・最小値の境界で正しく動作する
- [ ] 一意制約に違反する場合、適切に拒否される
- [ ] 外部ライブラリ（bcrypt など）の戻り値が正しい形式である
- [ ] テストが他のテストに依存しない（実行順序に依存しない）

### 4.2 リクエストスペック（コントローラー）

- [ ] 有効なリクエストで正しい HTTP ステータスが返る
- [ ] 無効なリクエストで正しい HTTP ステータスが返る
- [ ] レスポンスボディの JSON 構造が期待通りである
- [ ] レスポンスに機密情報が含まれない
- [ ] エラーレスポンスの構造が統一されている
- [ ] ルーティングが正しく解決される

### 4.3 統合・セキュリティ観点

- [ ] 認証失敗時のレスポンスが「存在の有無」を露呈しない
- [ ] タイミング攻撃のリスクを意識した設計になっている（現時点での妥協点も明示）
- [ ] セキュリティ関連のテストケースが漏れていない
- [ ] テストデータのクリーンアップが保証されている（DatabaseCleaner またはトランザクション）

## 5. 参考：テストケース命名規則

テスト名は「何を・どういう条件で・どうなるか」を簡潔に表現する。以下のパターンを基本とする。

### パターン

```
[条件] の場合、[結果] となる
[操作] すると、[結果] となる
```

### 例

| 悪い例 | 良い例 |
|---|---|
| `test user` | `有効なパラメータの場合、ユーザーを作成する` |
| `test authentication` | `正しいメール・パスワードの場合、ユーザーを返す` |
| `test password` | `誤ったパスワードの場合、nil を返す` |
| `test error` | `空のメールの場合、422 Unprocessable Entity を返す` |

**なぜこの命名か**

- テスト失敗時に「何が壊れたか」を即座に理解できる
- テスト名が仕様文書として機能する
- 他の開発者がテストを読む際に「このテストが何を保証しているか」を推測する必要がない
