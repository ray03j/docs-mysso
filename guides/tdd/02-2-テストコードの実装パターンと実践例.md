## 1. テストの構造パターン

### 1.1 AAAパターン（Arrange-Act-Assert）

テストの本体は必ず3つのステップに分ける。

```go
func TestUserService_Authenticate(t *testing.T) {
    // Arrange: テストデータと依存関係の準備
    user := testutil.NewUser("test@example.com", "password123")
    repo := testutil.NewInMemoryUserRepository()
    repo.Save(user)
    svc := NewUserService(repo)

    // Act: テスト対象の実行
    result, err := svc.Authenticate("test@example.com", "password123")

    // Assert: 結果の検証
    assert.NoError(t, err)
    assert.NotNil(t, result)
    assert.Equal(t, user.ID, result.ID)
}
```

**選定理由**
- テストの構造が統一され、読み手がすぐに「何をテストしているか」を理解できる。
- ステップが混在すると、テストの失敗時に「準備の問題か、実行の問題か、期待値の問題か」を判断しにくくなる。
- 単純なテストでも例外なく守ることで、コードレビュー時の認知負荷を下げる。

### 1.2 テーブル駆動テスト

同じロジックに対して複数の入力・期待値を網羅する場合、テーブル駆動を採用する。

```go
func TestPasswordValidator_Validate(t *testing.T) {
    tests := []struct {
        name     string
        password string
        wantErr  error
    }{
        {"空文字は拒否", "", ErrPasswordEmpty},
        {"短すぎる", "12345", ErrPasswordTooShort},
        {"妥当な長さ", "password123", nil},
        {"最大長超過", strings.Repeat("a", 129), ErrPasswordTooLong},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            err := PasswordValidator.Validate(tt.password)
            assert.ErrorIs(t, err, tt.wantErr)
        })
    }
}
```

**選定理由**
- ケースの追加が構造体への1行追加で済み、テスト関数の増加を防ぐ。
- `t.Run` により、どのケースが失敗したかが即座に判明する。
- 境界値（最小長、最大長、空文字）を並べて記述することで、網羅性を視覚的に確認できる。

**注意点**
- テーブルが10ケースを超える場合、テスト対象が「複数の責務を持っている」兆候として、対象の分割を検討する。
- 各ケースの `name` は「何をテストしているか」を説明する日本語（または英語のフレーズ）とする。

### 1.3 ネストされた構造 vs フラット構造

**ネストされた構造（go test のサブテスト）**

```go
func TestUserService(t *testing.T) {
    t.Run("Authenticate", func(t *testing.T) {
        t.Run("成功", func(t *testing.T) {
            // ...
        })
        t.Run("パスワード不一致", func(t *testing.T) {
            // ...
        })
    })
}
```

**フラット構造**

```go
func TestUserService_Authenticate_Success(t *testing.T) { /* ... */ }
func TestUserService_Authenticate_WrongPassword(t *testing.T) { /* ... */ }
```

**選定方針**
- フラット構造を基本とする。関数名で「何をテストするか」を明確に表現できる。
- ネストは「テスト対象が同じ前提条件を共有する」場合のみ使用する。例：同一のデータベース接続、同一のモックセットアップ。
- ネストの深さは2段階までとし、それ以上はテストの分割を検討する。

## 2. テストデータ構築パターン

### 2.1 Fixture関数

テストで使用するエンティティを生成するヘルパー関数。

```go
// testutil/fixture.go
package testutil

func NewUser(email, password string) *domain.User {
    return &domain.User{
        ID:        uuid.New(),
        Email:     email,
        Password:  password, // テスト用に平文を許容
        CreatedAt: time.Now(),
    }
}

func NewUserWithHashedPassword(email, plainPassword string) *domain.User {
    u := NewUser(email, plainPassword)
    hash, _ := bcrypt.GenerateFromPassword([]byte(plainPassword), bcrypt.DefaultCost)
    u.Password = string(hash)
    return u
}
```

**選定理由**
- テストコード内で「どのフィールドに何を入れるか」を毎回記述しない。
- デフォルト値を隠蔽しつつ、必要なフィールドだけ上書きできる。
- テストデータの生成ロジックを一元管理し、スキーマ変更時の修正点を最小化する。

### 2.2 Builderパターン

複雑なエンティティを段階的に構築する場合。

```go
user := testutil.NewUserBuilder().
    WithEmail("admin@example.com").
    WithRole(domain.RoleAdmin).
    WithVerified(true).
    Build()
```

**選定理由**
- フィールド数が多いエンティティ（User、Profile、Settings 等）で有効。
- 各メソッドが「何を設定するか」を明示的に表現し、可読性が高い。
- ビルダーが複雑になりすぎる場合は、Factory パターンへの移行を検討する。

### 2.3 Factoryパターン

ランダム・一意な値を持つエンティティを大量に生成する場合。

```go
users := testutil.NewUserFactory(10).Create() // 10人のユニークなユーザーを生成
```

**選定理由**
- 性能テストやページネーションのテストで、多数のデータが必要な場合に使用。
- 生成されるデータの内容はテストの関心事ではないため、Factory に任せる。
- テストの意図が「データの量」や「重複の有無」に焦点を当てる場合に適している。

## 3. モック・スタブの実装パターン

### 3.1 インターフェースによる分離

外部依存をテストから切り離すため、インターフェースを定義する。

```go
// 本番実装とテスト用モックの共通インターフェース
type UserRepository interface {
    FindByEmail(ctx context.Context, email string) (*User, error)
    Save(ctx context.Context, user *User) error
}

// 本番実装（PostgreSQL）
type PostgresUserRepository struct { /* ... */ }

// テスト用モック（インメモリ）
type InMemoryUserRepository struct { /* ... */ }
```

**選定理由**
- 実装の詳細（PostgreSQL か Redis か）をテストから隠蔽し、「どのような振る舞いを期待するか」に焦点を当てる。
- モックの実装を差し替えることで、エラーケース（DB接続失敗、タイムアウト）を簡単にシミュレートできる。

### 3.2 モックの実装例

```go
// testutil/mock_repository.go
package testutil

type InMemoryUserRepository struct {
    users map[string]*domain.User
    err   error // 強制的に返すエラー
}

func (r *InMemoryUserRepository) FindByEmail(ctx context.Context, email string) (*domain.User, error) {
    if r.err != nil {
        return nil, r.err
    }
    return r.users[email], nil
}

func (r *InMemoryUserRepository) Save(ctx context.Context, user *domain.User) error {
    if r.err != nil {
        return r.err
    }
    r.users[user.Email] = user
    return nil
}

// エラーを強制するヘルパー
func (r *InMemoryUserRepository) SetError(err error) {
    r.err = err
}
```

**選定理由**
- インメモリ実装は「実際の振る舞いに近い」ため、モックの偽陽性を減らせる。
- `SetError` メソッドにより、エラーケースを明示的にシミュレートできる。
- 生成ツール（mockery、gomock）を使う場合も、手書きモックと使い分ける。簡単なモックは手書きの方が可読性が高い。

### 3.3 モックの検証ポイント

モックを使うテストでは、以下を検証する。

- **戻り値の検証**: モックが期待する値を返した場合、テスト対象が正しく処理するか。
- **エラーケースの検証**: モックがエラーを返した場合、テスト対象が適切にエラーハンドリングするか。
- **呼び出し回数の検証（必要な場合のみ）**: 特定のメソッドが「一度だけ呼ばれるべき」場合（例：メール送信、課金処理）に限り、呼び出し回数を検証する。

**避けるべき検証**
- 内部実装の「細かい呼び出し順序」を検証する。リファクタリングで壊れやすい。
- データアクセスの「クエリ文字列」を検証する。ORM の内部動作に依存しすぎる。

## 4. エラー・例外のテストパターン

### 4.1 期待するエラーの検証

```go
func TestUserService_Authenticate_UserNotFound(t *testing.T) {
    repo := testutil.NewInMemoryUserRepository()
    svc := NewUserService(repo)

    _, err := svc.Authenticate("notfound@example.com", "password")

    assert.ErrorIs(t, err, ErrUserNotFound)
}
```

**選定理由**
- `errors.Is` を使い、エラーの「型」または「定義済み変数」で検証する。エラーメッセージの文字列比較は避ける（メッセージ変更でテストが壊れる）。
- エラー変数はエクスポート（export）し、テストパッケージやクライアントからも判別できるようにする。

### 4.2 エラーメッセージの検証

エラーメッセージ自体が「API のレスポンスやログに露出する」場合、内容を検証する。

```go
func TestUserService_Authenticate_InvalidPassword(t *testing.T) {
    // Arrange
    user := testutil.NewUserWithHashedPassword("test@example.com", "correct")
    repo := testutil.NewInMemoryUserRepository()
    repo.Save(user)
    svc := NewUserService(repo)

    // Act
    _, err := svc.Authenticate("test@example.com", "wrong")

    // Assert
    assert.ErrorIs(t, err, ErrInvalidPassword)
    assert.Contains(t, err.Error(), "invalid password")
}
```

**選定理由**
- エラーメッセージは「ユーザーに表示される可能性がある」ため、意図した内容であることを検証する。
- メッセージの検証は「含む文字列」を使い、完全一致は避ける。フォーマットの変更に柔軟に対応する。

### 4.3 エラーチェーンの検証

エラーがラップされて伝播する場合、チェーンを検証する。

```go
func TestUserService_Authenticate_RepositoryError(t *testing.T) {
    repo := testutil.NewInMemoryUserRepository()
    repo.SetError(errors.New("db connection failed"))
    svc := NewUserService(repo)

    _, err := svc.Authenticate("test@example.com", "password")

    assert.ErrorIs(t, err, ErrInternal)
    assert.Contains(t, err.Error(), "db connection failed")
    
    // エラーチェーンの確認
    var repoErr *RepositoryError
    assert.ErrorAs(t, err, &repoErr)
}
```

## 5. 非同期・並列処理のテストパターン

### 5.1 ゴルーチンのテスト

非同期処理の結果を検証する場合、チャネルまたは `sync.WaitGroup` を使って同期する。

```go
func TestUserService_SendEmailAsync(t *testing.T) {
    svc := NewUserService()
    done := make(chan error, 1)

    svc.SendEmailAsync("test@example.com", func(err error) {
        done <- err
    })

    select {
    case err := <-done:
        assert.NoError(t, err)
    case <-time.After(2 * time.Second):
        t.Fatal("タイムアウト")
    }
}
```

**選定理由**
- ゴルーチンの終了を待たずにテストを終えると、リソースリークやテストの flakiness が生じる。
- チャネルによる同期は、テストコードが「実際の非同期処理の流れ」を表現し、可読性が高い。

### 5.2 タイムアウトのテスト

時間に依存する処理（キャッシュの TTL、トークンの有効期限）をテストする場合、時間を制御する。

```go
func TestToken_Expired(t *testing.T) {
    clock := testutil.NewFakeClock(time.Now())
    token := NewTokenWithClock("user-id", 1*time.Hour, clock)

    assert.False(t, token.IsExpired())

    clock.Advance(2 * time.Hour) // 時間を進める

    assert.True(t, token.IsExpired())
}
```

**選定理由**
- `time.Sleep` を使うテストは遅く、flaky になりやすい。
- インジェクション可能な `Clock` インターフェースを定義し、テストでは「偽の時間」を使う。

### 5.3 競合状態のテスト

```go
func TestUserService_ConcurrentUpdate(t *testing.T) {
    repo := testutil.NewInMemoryUserRepository()
    svc := NewUserService(repo)
    user := testutil.NewUser("test@example.com", "password")
    repo.Save(user)

    var wg sync.WaitGroup
    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            svc.UpdateProfile(user.ID, fmt.Sprintf("name-%d", id))
        }(i)
    }
    wg.Wait()

    // 結果の検証（楽観ロックの確認など）
    updated, _ := repo.FindByID(user.ID)
    assert.NotNil(t, updated)
}
```

**選定理由**
- `go test -race` と併用し、データ競合を検出する。
- 競合テストは「結果の整合性」を検証するのではなく、「データ競合が発生しないこと」を目的とする。

## 6. テストの可読性と保守性

### 6.1 命名規則

- **ファイル名**: `対象ファイル名_test.go`
- **関数名**: `Test対象の構造体_メソッド名_シナリオ`（例: `TestUserService_Authenticate_Success`）
- **テーブル駆動の name**: `英語または日本語の説明文`（例: `"空文字は拒否"`、`"user not found returns error"`）
- **変数名**: `want`（期待値）、`got`（実際の値）、`tt`（テーブルの要素）を一貫して使用する。

### 6.2 ヘルパー関数の抽出

テスト内で3回以上出現する構造は、ヘルパー関数に抽出する。

```go
// テスト用のサービスインスタンスを構築
func newTestUserService(t *testing.T, repo UserRepository) *UserService {
    t.Helper()
    return NewUserService(repo, testutil.NewFakeClock(time.Now()))
}

// テスト用のコンテキストを生成
func newTestContext(t *testing.T) context.Context {
    t.Helper()
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    t.Cleanup(cancel)
    return ctx
}
```

**選定理由**
- `t.Helper()` を付けることで、テスト失敗時のスタックトレースからヘルパー関数が除外され、実際の失敗行がわかりやすくなる。
- `t.Cleanup` を使うことで、テストの終了時にリソース（DB接続、一時ファイル）を自動解放できる。

### 6.3 重複排除のバランス

「DRY（Don't Repeat Yourself）」はテストコードでも有効だが、過度な抽象化は避ける。

**適切な抽象化**
- テストデータの生成（Fixture、Builder）
- 共通の前提条件（ヘルパー関数）
- 繰り返し出現するアサーション（カスタムアサーション関数）

**避けるべき抽象化**
- テストケースの「Arrange」部分を完全に外部化する。テストの「何を準備しているか」を読み手が追わなければならなくなる。
- 複数のテストで「1つのヘルパー関数」が全ての準備を行う（「神関数」）。変更の影響範囲が不明確になる。

## 7. 実践例：IdP User Service

### 7.1 認証サービスのテスト

```go
package service

import (
    "testing"
    "github.com/stretchr/testify/assert"
    "idp-user-service/testutil"
)

func TestAuthenticationService_Authenticate_Success(t *testing.T) {
    // Arrange
    user := testutil.NewUserWithHashedPassword("test@example.com", "password123")
    repo := testutil.NewInMemoryUserRepository()
    repo.Save(user)
    svc := NewAuthenticationService(repo)

    // Act
    result, err := svc.Authenticate("test@example.com", "password123")

    // Assert
    assert.NoError(t, err)
    assert.Equal(t, user.ID, result.UserID)
    assert.NotEmpty(t, result.Token)
}

func TestAuthenticationService_Authenticate_WrongPassword(t *testing.T) {
    // Arrange
    user := testutil.NewUserWithHashedPassword("test@example.com", "password123")
    repo := testutil.NewInMemoryUserRepository()
    repo.Save(user)
    svc := NewAuthenticationService(repo)

    // Act
    _, err := svc.Authenticate("test@example.com", "wrongpassword")

    // Assert
    assert.ErrorIs(t, err, ErrInvalidCredentials)
}

func TestAuthenticationService_Authenticate_UserNotFound(t *testing.T) {
    // Arrange
    repo := testutil.NewInMemoryUserRepository()
    svc := NewAuthenticationService(repo)

    // Act
    _, err := svc.Authenticate("notfound@example.com", "password123")

    // Assert
    assert.ErrorIs(t, err, ErrUserNotFound)
}
```

### 7.2 リポジトリのテスト

```go
package repository

import (
    "context"
    "testing"
    "github.com/stretchr/testify/assert"
    "github.com/stretchr/testify/require"
    "idp-user-service/testutil"
)

func TestPostgresUserRepository_FindByEmail(t *testing.T) {
    db := testutil.NewTestDB(t)
    repo := NewPostgresUserRepository(db)
    ctx := context.Background()

    // テストデータを投入
    user := testutil.NewUserWithHashedPassword("test@example.com", "password")
    err := repo.Save(ctx, user)
    require.NoError(t, err)

    // 検索
    found, err := repo.FindByEmail(ctx, "test@example.com")
    
    assert.NoError(t, err)
    assert.Equal(t, user.ID, found.ID)
    assert.Equal(t, user.Email, found.Email)
}

func TestPostgresUserRepository_Save_DuplicateEmail(t *testing.T) {
    db := testutil.NewTestDB(t)
    repo := NewPostgresUserRepository(db)
    ctx := context.Background()

    user1 := testutil.NewUser("test@example.com", "password1")
    user2 := testutil.NewUser("test@example.com", "password2")
    
    require.NoError(t, repo.Save(ctx, user1))
    
    err := repo.Save(ctx, user2)
    assert.ErrorIs(t, err, ErrDuplicateEmail)
}
```

### 7.3 APIハンドラのテスト

```go
package handler

import (
    "bytes"
    "encoding/json"
    "net/http"
    "net/http/httptest"
    "testing"
    "github.com/stretchr/testify/assert"
    "idp-user-service/testutil"
)

func TestAuthHandler_Login(t *testing.T) {
    // Arrange
    user := testutil.NewUserWithHashedPassword("test@example.com", "password")
    repo := testutil.NewInMemoryUserRepository()
    repo.Save(user)
    svc := testutil.NewAuthenticationService(repo)
    handler := NewAuthHandler(svc)

    body := `{"email":"test@example.com","password":"password"}`
    req := httptest.NewRequest(http.MethodPost, "/api/v1/login", bytes.NewReader([]byte(body)))
    req.Header.Set("Content-Type", "application/json")
    rec := httptest.NewRecorder()

    // Act
    handler.Login(rec, req)

    // Assert
    assert.Equal(t, http.StatusOK, rec.Code)
    
    var resp LoginResponse
    err := json.Unmarshal(rec.Body.Bytes(), &resp)
    assert.NoError(t, err)
    assert.NotEmpty(t, resp.Token)
    assert.Equal(t, "test@example.com", resp.Email)
}

func TestAuthHandler_Login_InvalidJSON(t *testing.T) {
    svc := testutil.NewAuthenticationService(nil)
    handler := NewAuthHandler(svc)
```

## 8. まとめ

テストコードの実装において、以下のパターンを標準とする。

1. **AAAパターンとテーブル駆動テストを基本とし、テストの構造を統一する。**
2. **Fixture・Builder・Factory を使い、テストデータの構築を抽象化する。**
3. **インターフェースによる分離と、必要最小限のモックで外部依存を制御する。**
4. **エラーは型で判別し、時間依存処理は Clock インターフェースで制御する。**
5. **ヘルパー関数で重複を排除しつつ、テストの「何を準備しているか」を読み手に伝える。**

これにより、テストコードは「実行可能な仕様書」として機能し、変更に対する回復力と開発速度を両立する。
