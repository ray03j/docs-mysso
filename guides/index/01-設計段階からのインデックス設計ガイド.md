## なぜ設計段階からインデックスを考えるのか

インデックスは「後から貼ればいい」と考えがちですが、以下の理由から設計段階で考えるべきです。

- **データ増加後の `CREATE INDEX` は高コスト**: テーブルロックやレプリケーション遅延が発生する
- **`UNIQUE` 制約の後付けは困難**: 既存の重複データをクリーニングする必要がある
- **アクセスパターンはスキーマと不可分**: どのカラムで検索・結合・一意制約が必要かは、テーブル構造を決める時点で既に決まっている

## インデックス設計の3つの質問

カラムを1つ追加するたびに、以下の3つを必ず問います。

### 1. Where — このカラムで `WHERE` 検索はするか？

`WHERE` 句で頻繁に絞り込みに使うカラムはインデックスの第一候補です。

### 2. Join — このカラムで他テーブルと `JOIN` するか？

外部キーに相当するカラムは、結合性能のためにインデックスを検討します。

### 3. Unique — このカラムの値はアプリケーション的に一意にすべきか？

メールアドレス、トークン、クライアントIDなど、重複を許さないカラムには `UNIQUE` インデックスを設定します。

## アクセスパターンからインデックスを導く

インデックスは「データ構造」ではなく「クエリ構造」に対して設計します。テーブル定義が固まったら、そのテーブルを使う主要なクエリを3〜5個先に書いてみます。

### 実例: `idp-auth` の `access_tokens` テーブル

```sql
-- 1. トークン検証（最も頻度高い）
SELECT * FROM access_tokens WHERE token = ? AND expires_at > NOW();

-- 2. ユーザーの有効なトークンを全て取得（ログアウト時の revoke 等）
SELECT * FROM access_tokens WHERE user_id = ? AND client_id = ?;

-- 3. 古いトークンの削除（バッチ処理）
DELETE FROM access_tokens WHERE expires_at < NOW();
```

これを書けば、以下のインデックスが必要なことが設計段階で自明になります。

| インデックス | 理由 |
|---|---|
| `token` (unique) | クエリ1の `WHERE token = ?` で検索 + トークンの重複不可 |
| `user_id`, `client_id` (複合) | クエリ2の `WHERE user_id = ? AND client_id = ?` で検索 |

### 実例: `idp-auth` の `authorization_codes` テーブル

```sql
-- 1. 認可コードの検証
SELECT * FROM authorization_codes WHERE code = ?;

-- 2. 特定クライアントの未使用コードをクリーンアップ
SELECT * FROM authorization_codes WHERE client_id = ? AND used = false;
```

| インデックス | 理由 |
|---|---|
| `code` (unique) | クエリ1の `WHERE code = ?` で検索 + コードの重複不可 |
| `client_id`, `used` (複合) | クエリ2の `WHERE client_id = ? AND used = ?` で検索 |

## マイグレーションのベストプラクティス

### `create_table` のブロック内にインデックス定義を必ず含める

インデックスを同じマイグレーションに書くことで、設計と同時に定義が完了します。

```ruby
# 悪い例（後で忘れる）
create_table :authorization_codes do |t|
  t.string :code
  t.integer :client_id
  t.boolean :used
end
# 後から別マイグレーションで add_index する → 忘れがち

# 良い例（設計と同時に）
create_table :authorization_codes do |t|
  t.string :code, null: false
  t.integer :client_id, null: false
  t.boolean :used, default: false, null: false

  t.index :code, unique: true
  t.index [:client_id, :used]
end
```

### 複合インデックスの順序

複合インデックスでは、**等価比較 (`=`) に使うカラムを先に、範囲比較 (`>`, `<`, `BETWEEN`) に使うカラムを後に** 配置します。

```ruby
# 良い: client_id は等価、used も等価
t.index [:client_id, :used]

# 悪い: expires_at は範囲比較なので先に置くと後続カラムが使われにくい
t.index [:expires_at, :user_id]
```

## まとめ

1. **カラム追加時に「Where / Join / Unique」を問う**
2. **テーブル設計後に主要クエリを先に書く**
3. **マイグレーションのテンプレートにインデックス欄を必ず含める**

これを3回〜5回繰り返すと、自然と「このカラムは index 対象だ」と設計段階で感じるようになります。
