## インデックス詳細解説

以下の解説で使用する `code`, `client_id`, `used`, `user_id`, `token` などのカラム名は、上記各マイグレーション（`001_create_authorization_codes.rb` 〜 `004_create_consents.rb`）の `create_table` ブロック内で定義されたものです。

以下、各テーブルに定義したインデックスの動作原理を `docs-mysso/knowledge-base/01-composite-index-mechanism.md` と同じ構成で解説する。

---

### A. `authorization_codes` テーブル

#### A-1. `code`（単一カラム UNIQUE インデックス）

##### A-1.1 結論

`code` への単一 UNIQUE インデックスは、**B-Tree による階層的索引構造**でデータを管理します。

- `code` の文字列順でソートされた木構造
- 重複値の挿入を即座に検出（UNIQUE 制約）
- 葉ノードから実テーブル行ID（ポインタ）を取得しジャンプ

##### A-1.2 なぜインデックスが必要か

認可コードフローでは、クライアントから受け取った `code` で即座にレコードを検索する必要があります。

| 検索シナリオ | 例 |
|---|---|
| 認可コードの検証 | `code='abc123'` |
| コード再利用攻撃の防止 | 使用済みコードの即時判定 |

**インデックスなし**ではフルスキャンが発生し、認可コードの総数に比例して遅くなります。

##### A-1.3 インデックスの内部構造

###### 前提データ

| id | code | client_id | used |
|---|---|---|---|
| 1 | abc123 | client_A | false |
| 2 | def456 | client_A | true |
| 3 | ghi789 | client_B | false |

###### B-Tree の構造

```
                    ┌─────────────┐
                    │    code     │
                    └──────┬──────┘
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
      ┌─────────┐    ┌─────────┐    ┌─────────┐
      │  abc123 │    │  def456 │    │  ghi789 │
      └────┬────┘    └────┬────┘    └────┬────┘
           ▼               ▼               ▼
         id=1            id=2            id=3
```

**各葉ノードには「実テーブルの行ID（ポインタ）」が記録されています。**

##### A-1.4 検索時の動き

###### クエリ

```sql
SELECT * FROM authorization_codes
WHERE code = 'abc123';
```

###### 実行ステップ

```
Step 1: 木の根から code='abc123' の枝を辿る
        → def456, ghi789 の枝は完全に無視

Step 2: 到達した葉ノードからポインタを取得
        → id=1

Step 3: 実テーブルの id=1 の行を読み取る
        → 1行だけアクセスで完了
```

| ステップ | 読むレコード数 | 操作 |
|---|---|---|
| 1〜2（索引探索） | 木の高さに比例 | B-Treeを辿るだけ |
| 3（実テーブル） | 該当1行 | ポインタで直接ジャンプ |

##### A-1.5 インデックスと実テーブルの関係

**インデックスは実データの「地図」です。**

###### 実テーブル（データそのもの）

```
┌──────────────────────────────────────────────┐
│  authorization_codes（実テーブル）            │
├────┬─────────┬───────────┬───────┬───────────┤
│ id │ code    │ client_id │ used  │ expires_at│
├────┼─────────┼───────────┼───────┼───────────┤
│  1 │ abc123  │ client_A  │ false │ 10:00     │
│  2 │ def456  │ client_A  │ true  │ 10:05     │
│  3 │ ghi789  │ client_B  │ false │ 10:10     │
└────┴─────────┴───────────┴───────┴───────────┘
```

###### 単一インデックス（別の構造）

```
┌──────────────────────────────────────────────┐
│  インデックス [code] UNIQUE                   │
├─────────────────────┬────────────────────────┤
│  検索キー           │  実テーブルへのポインタ │
├─────────────────────┼────────────────────────┤
│ abc123              │ → id=1                 │
│ def456              │ → id=2                 │
│ ghi789              │ → id=3                 │
└─────────────────────┴────────────────────────┘
```

**インデックスに含まれるもの**

| 含まれる | 含まれない |
|---|---|
| `code` の値 | `client_id` の値 |
| 実テーブルの行ID（ポインタ） | `used`, `expires_at` の値 |

##### A-1.6 まとめ

| 項目 | 内容 |
|---|---|
| **目的** | 認可コードを一意に・高速に検索 |
| **仕組み** | B-Tree による階層的な索引構造 |
| **UNIQUE の効果** | 同じコードの重複登録を物理的に防ぐ |
| **検索の流れ** | 索引を辿る → ポインタ取得 → 実テーブルへジャンプ |

#### A-2. `[client_id, used]`（複合インデックス）

##### A-2.1 結論

複合インデックス `[client_id, used]` は、**B-Tree という階層的な索引構造**でデータを管理します。

- `client_id` で大きく枝分かれし、無関係なクライアントを一括除外
- `used` でさらに細分化し、未使用コードだけに絞り込み
- 目的のレコードへの**ポインタ**を取得し、実テーブルにジャンプ

結果、数万行のテーブルでも**木の高さ（3〜4層）を辿るだけ**で検索が完了します。

##### A-2.2 なぜインデックスが必要か

`authorization_codes` テーブルは OIDC 認可コードフローで頻繁に検索されます。

| 検索シナリオ | 例 |
|---|---|
| 未使用コードの検証 | `client_id='A' AND used=false` |
| クライアント別の未使用コード一覧 | 管理画面での確認 |
| 期限切れコードのクリーンアップ | バッチジョブでの一括削除 |

**インデックスなし**ではテーブル先頭から1行ずつ読む「フルスキャン」が発生し、レコード数に比例して遅くなります。

##### A-2.3 インデックスの内部構造

###### 前提データ

| id | code | client_id | used |
|---|---|---|---|
| 1 | abc123 | client_A | false |
| 2 | def456 | client_A | true |
| 3 | ghi789 | client_B | false |
| 4 | jkl012 | client_A | false |
| 5 | mno345 | client_B | true |

###### B-Tree の構造

複合インデックス `[client_id, used]` は内部的に以下の木構造になります。

```
                    ┌─────────────┐
                    │  client_id  │
                    └──────┬──────┘
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
      ┌─────────┐    ┌─────────┐    ┌─────────┐
      │client_A │    │client_B │    │client_C │
      └────┬────┘    └────┬────┘    └─────────┘
      ┌────┴────┐    ┌────┴────┐
      ▼         ▼    ▼         ▼
   ┌──────┐  ┌──────┐ ┌──────┐  ┌──────┐
   │false │  │true  │ │false │  │true  │
   └──┬───┘  └──┬───┘ └──┬───┘  └──┬───┘
      ▼         ▼        ▼         ▼
    id=1      id=2     id=3      id=5
    id=4
```

**各葉ノードには「実テーブルの行ID（ポインタ）」が記録されています。**

##### A-2.4 検索時の動き

###### クエリ

```sql
SELECT * FROM authorization_codes
WHERE client_id = 'client_A' AND used = false;
```

###### 実行ステップ

```
Step 1: 木の根から client_id='client_A' の枝を辿る
        → client_B, client_C の枝は完全に無視

Step 2: client_A の枝の中から used=false の枝を辿る
        → used=true の枝は無視

Step 3: 到達した葉ノードからポインタを取得
        → id=1, id=4

Step 4: 実テーブルの id=1, id=4 の行を読み取る
        → 2行だけアクセスで完了
```

| ステップ | 読むレコード数 | 操作 |
|---|---|---|
| 1〜3（索引探索） | 木の高さに比例 | B-Treeを辿るだけ |
| 4（実テーブル） | 該当2行 | ポインタで直接ジャンプ |

##### A-2.5 なぜ列順が重要か

複合インデックスは**左端のカラムから順にしか効果を発揮しません**。

###### 現在の設計：`[client_id, used]`（推奨）

```
【第1層：client_id で分岐】
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
    client_A    client_B    client_C
    （数千〜数万分の1に絞る）
        │
        └─ 第2層：used でさらに2分の1に絞る
```

- `client_id` のカーディナリティ（選択率）は**高い**（数千〜数万種類）
- 第1層で**大半の枝を一括切り落とせる**

###### 仮に順序を逆にした場合：`[used, client_id]`（非推奨）

```
【第1層：used で分岐】
                    │
            ┌───────┴───────┐
            ▼               ▼
          false           true
        （全体の約半分）  （全体の約半分）
            │
            └─ 第2層：client_id で細分化
               → それでもまだ大量の枝が残る
```

- `used` は boolean なのでカーディナリティは**極めて低い**（true/false のみ）
- 第1層で**枝をほとんど切り落とせない**

###### 比較

| インデックス順序 | 第1層の絞り込み効果 | 評価 |
|---|---|---|
| `[client_id, used]` | **高い**（数千〜数万に分岐） | ✅ 最適 |
| `[used, client_id]` | **低い**（2分岐のみ） | ❌ 非効率 |

##### A-2.6 インデックスと実テーブルの関係

**インデックスは実データの「複製」ではなく「地図」です。**

###### 実テーブル（データそのもの）

```
┌──────────────────────────────────────────────┐
│  authorization_codes（実テーブル）            │
├────┬─────────┬───────────┬───────┬───────────┤
│ id │ code    │ client_id │ used  │ expires_at│
├────┼─────────┼───────────┼───────┼───────────┤
│  1 │ abc123  │ client_A  │ false │ 10:00     │
│  2 │ def456  │ client_A  │ true  │ 10:05     │
│  3 │ ghi789  │ client_B  │ false │ 10:10     │
│  4 │ jkl012  │ client_A  │ false │ 10:15     │
│  5 │ mno345  │ client_B  │ true  │ 10:20     │
└────┴─────────┴───────────┴───────┴───────────┘
```

###### 複合インデックス（別の構造）

```
┌──────────────────────────────────────────────┐
│  インデックス [client_id, used]               │
├─────────────────────┬────────────────────────┤
│  検索キー           │  実テーブルへのポインタ │
├─────────────────────┼────────────────────────┤
│ (client_A, false)   │ → id=1                 │
│ (client_A, false)   │ → id=4                 │
│ (client_A, true)    │ → id=2                 │
│ (client_B, false)   │ → id=3                 │
│ (client_B, true)    │ → id=5                 │
└─────────────────────┴────────────────────────┘
```

**インデックスに含まれるもの**

| 含まれる | 含まれない |
|---|---|
| `client_id` の値 | `code` の文字列 |
| `used` の値 | `expires_at` の値 |
| 実テーブルの行ID（ポインタ） | その他のカラムデータ |

##### A-2.7 まとめ

| 項目 | 内容 |
|---|---|
| **目的** | 「どのクライアントの、未使用コードか」を高速に検索 |
| **仕組み** | B-Tree による階層的な索引構造 |
| **列順の理由** | `client_id` の方がカーディナリティが高く、絞り込み効果が大きい |
| **検索の流れ** | 索引を辿る → ポインタ取得 → 実テーブルへジャンプ |
| **制約** | `WHERE` 句に `client_id` を含めないと索引が使えない |

> 複合インデックスは「地図」です。正しい順序で地図を引けば、目的の場所に最短ルートで到達できます。

```
    （数万〜数百万分の1に絞る）
        │
```

- `user_id` のカーディナリティ（選択率）は**高い**（数万〜数百万種類）
- 第1層で**大半の枝を一括切り落とせる**
- さらに `client_id` で細分化し、対象クライアントに絞り込む

###### 仮に順序を逆にした場合：`[client_id, user_id]`（非推奨）

```
【第1層：client_id で分岐】

            ┌───────┴───────┐
            ▼               ▼
         client_A        client_B
        （数十〜数百種類）
            │

               → 人気クライアントの枝には大量のユーザーが残る
```

- `client_id` のカーディナリティは**低い**（数十〜数百種類）
- 人気クライアント（例: `demo_client`）の枝には**大量のユーザー**が紐づく
- 第1層の絞り込み効果が**小さい**

###### 比較

| インデックス順序 | 第1層の絞り込み効果 | 評価 |
|---|---|---|
| `[user_id, client_id]` | **高い**（数万〜数百万に分岐） | ✅ 最適 |
| `[client_id, user_id]` | **低い**（数十〜数百に分岐、人気クライアントは大量） | ❌ 非効率 |

### C. `refresh_tokens` テーブル

```
        │
        └─ 第2層：client_id でさらに絞る
```

- `user_id` のカーディナリティ（選択率）は**高い**（数万〜数百万種類）
- 第1層で**大半の枝を一括切り落とせる**
- さらに `client_id` で細分化し、対象クライアントに絞り込む

###### 仮に順序を逆にした場合：`[client_id, user_id]`（非推奨）

```
【第1層：client_id で分岐】
                    │
            ┌───────┴───────┐
            ▼               ▼
         client_A        client_B
        （数十〜数百種類）
            │
            └─ 第2層：user_id で細分化
               → 人気クライアントの枝には大量のユーザーが残る
```

- `client_id` のカーディナリティは**低い**（数十〜数百種類）
- 人気クライアント（例: `demo_client`）の枝には**大量のユーザー**が紐づく
- 第1層の絞り込み効果が**小さい**

###### 比較

| インデックス順序 | 第1層の絞り込み効果 | 評価 |
|---|---|---|
| `[user_id, client_id]` | **高い**（数万〜数百万に分岐） | ✅ 最適 |
| `[client_id, user_id]` | **低い**（数十〜数百に分岐、人気クライアントは大量） | ❌ 非効率 |

##### D-1.6 UNIQUE 制約の動作

**B-Tree による重複検出**

`consents` テーブルへの挿入時、データベースは以下のステップで重複を検出します。

```
Step 1: 挿入しようとする (user_id, client_id) の値で B-Tree を辿る

Step 2: 到達した葉ノードに同じ値が存在するか確認
        → 存在する場合：UNIQUE 違反エラーを返す
        → 存在しない場合：新しい葉ノードを追加
```

| 操作 | コスト |
|---|---|
| 重複チェック | B-Tree 探索と同じ（木の高さに比例） |
| 新規挿入 | 葉ノード追加（索引更新） |

つまり、**UNIQUE 制約の重複チェックは索引探索と同じコスト**で完了します。フルスキャンは発生しません。

##### D-1.7 インデックスと実テーブルの関係

**インデックスは実データの「複製」ではなく「地図」です。**

###### 実テーブル（データそのもの）

```
┌──────────────────────────────────────────────┐
│  consents（実テーブル）                       │
├────┬─────────┬───────────┬───────────────────┤
│ id │ user_id │ client_id │ scope             │
├────┼─────────┼───────────┼───────────────────┤
│  1 │ user_1  │ client_A  │ openid profile    │
│  2 │ user_1  │ client_B  │ openid email      │
│  3 │ user_2  │ client_A  │ openid            │
└────┴─────────┴───────────┴───────────────────┘
```

###### 複合インデックス（別の構造）

```
┌──────────────────────────────────────────────┐
│  インデックス [user_id, client_id] UNIQUE     │
├─────────────────────┬────────────────────────┤
│  検索キー           │  実テーブルへのポインタ │
├─────────────────────┼────────────────────────┤
│ (user_1, client_A)  │ → id=1                 │
│ (user_1, client_B)  │ → id=2                 │
│ (user_2, client_A)  │ → id=3                 │
└─────────────────────┴────────────────────────┘
```

**インデックスに含まれるもの**

| 含まれる | 含まれない |
|---|---|
| `user_id` の値 | `scope` の文字列 |
| `client_id` の値 | その他のカラムデータ |
| 実テーブルの行ID（ポインタ） | |

##### D-1.8 まとめ

| 項目 | 内容 |
|---|---|
| **目的** | 「どのユーザーの、どのクライアントへの同意か」を高速に検索・一意に管理 |
| **仕組み** | B-Tree による階層的な索引構造 |
| **列順の理由** | `user_id` の方がカーディナリティが高く、絞り込み効果が大きい |
| **UNIQUE の効果** | 同一ユーザー・同一クライアントの重複レコード挿入を防ぐ |
| **検索の流れ** | 索引を辿る → ポインタ取得 → 実テーブルへジャンプ |
| **制約** | `WHERE` 句に `user_id` を含めないと索引が使えない |

> 複合インデックスは「地図」です。正しい順序で地図を引けば、目的の場所に最短ルートで到達できます。UNIQUE 制約は「地図上で同じ場所を二重に登録しない」約束です。
