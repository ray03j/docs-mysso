## 1. 結論

複合インデックス `[client_id, used]` は、**B-Tree という階層的な索引構造**でデータを管理します。

- `client_id` で大きく枝分かれし、無関係なクライアントを一括除外
- `used` でさらに細分化し、未使用コードだけに絞り込み
- 目的のレコードへの**ポインタ**を取得し、実テーブルにジャンプ

結果、数万行のテーブルでも**木の高さ（3〜4層）を辿るだけ**で検索が完了します。

---

## 2. なぜインデックスが必要か

`authorization_codes` テーブルは OIDC 認可コードフローで頻繁に検索されます。

| 検索シナリオ | 例 |
|---|---|
| 未使用コードの検証 | `client_id='A' AND used=false` |
| クライアント別の未使用コード一覧 | 管理画面での確認 |
| 期限切れコードのクリーンアップ | バッチジョブでの一括削除 |

**インデックスなし**ではテーブル先頭から1行ずつ読む「フルスキャン」が発生し、レコード数に比例して遅くなります。

## 3. インデックスの内部構造

### 3.1 前提データ

| id | code | client_id | used |
|---|---|---|---|
| 1 | abc123 | client_A | false |
| 2 | def456 | client_A | true |
| 3 | ghi789 | client_B | false |
| 4 | jkl012 | client_A | false |
| 5 | mno345 | client_B | true |

### 3.2 B-Tree の構造

複合インデックス `[client_id, used]` は内部的に以下の木構造になります。

```
                    ┌─────────────┐
                    │  client_id  │
                    └──────┬──────┘
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
      ┌─────────┐    ┌─────────┐    ┌─────────┐
      │client_A │    │client_B │    │client_C │
      └────┬────┘    └────┬────┘    └─────────┘
      ┌────┴────┐    ┌────┴────┐
      ▼         ▼    ▼         ▼
   ┌──────┐  ┌──────┐ ┌──────┐  ┌──────┐
   │false │  │true  │ │false │  │true  │
   └──┬───┘  └──┬───┘ └──┬───┘  └──┬───┘
      ▼         ▼        ▼         ▼
    id=1      id=2     id=3      id=5
    id=4
```

**各葉ノードには「実テーブルの行ID（ポインタ）」が記録されています。**

---

## 4. 検索時の動き

### クエリ

```sql
SELECT * FROM authorization_codes
WHERE client_id = 'client_A' AND used = false;
```

### 実行ステップ

```
Step 1: 木の根から client_id='client_A' の枝を辿る
        → client_B, client_C の枝は完全に無視

Step 2: client_A の枝の中から used=false の枝を辿る
        → used=true の枝は無視

Step 3: 到達した葉ノードからポインタを取得
        → id=1, id=4

Step 4: 実テーブルの id=1, id=4 の行を読み取る
        → 2行だけアクセスで完了
```

| ステップ | 読むレコード数 | 操作 |
|---|---|---|
| 1〜3（索引探索） | 木の高さに比例 | B-Treeを辿るだけ |
| 4（実テーブル） | 該当2行 | ポインタで直接ジャンプ |

## 5. なぜ列順が重要か

複合インデックスは**左端のカラムから順にしか効果を発揮しません**。

### 現在の設計：`[client_id, used]`（推奨）

```
【第1層：client_id で分岐】
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
    client_A    client_B    client_C
    （数千〜数万分の1に絞る）
        │
        └─ 第2層：used でさらに2分の1に絞る
```

- `client_id` のカーディナリティ（選択率）は**高い**（数千〜数万種類）
- 第1層で**大半の枝を一括切り落とせる**

### 仮に順序を逆にした場合：`[used, client_id]`（非推奨）

```
【第1層：used で分岐】
                    │
            ┌───────┴───────┐
            ▼               ▼
          false           true
        （全体の約半分）  （全体の約半分）
            │
            └─ 第2層：client_id で細分化
               → それでもまだ大量の枝が残る
```

- `used` は boolean なのでカーディナリティは**極めて低い**（true/false のみ）
- 第1層で**枝をほとんど切り落とせない**

### 比較

| インデックス順序 | 第1層の絞り込み効果 | 評価 |
|---|---|---|
| `[client_id, used]` | **高い**（数千〜数万に分岐） | ✅ 最適 |
| `[used, client_id]` | **低い**（2分岐のみ） | ❌ 非効率 |

## 6. インデックスと実テーブルの関係

**インデックスは実データの「複製」ではなく「地図」です。**

### 実テーブル（データそのもの）

```
┌──────────────────────────────────────────────┐
│  authorization_codes（実テーブル）            │
├────┬─────────┬───────────┬───────┬───────────┤
│ id │ code    │ client_id │ used  │ expires_at│
├────┼─────────┼───────────┼───────┼───────────┤
│  1 │ abc123  │ client_A  │ false │ 10:00     │
│  2 │ def456  │ client_A  │ true  │ 10:05     │
│  3 │ ghi789  │ client_B  │ false │ 10:10     │
│  4 │ jkl012  │ client_A  │ false │ 10:15     │
│  5 │ mno345  │ client_B  │ true  │ 10:20     │
└────┴─────────┴───────────┴───────┴───────────┘
```

### 複合インデックス（別の構造）

```
┌──────────────────────────────────────────────┐
│  インデックス [client_id, used]               │
├─────────────────────┬────────────────────────┤
│  検索キー           │  実テーブルへのポインタ │
├─────────────────────┼────────────────────────┤
│ (client_A, false)   │ → id=1                 │
│ (client_A, false)   │ → id=4                 │
│ (client_A, true)    │ → id=2                 │
│ (client_B, false)   │ → id=3                 │
│ (client_B, true)    │ → id=5                 │
└─────────────────────┴────────────────────────┘
```

**インデックスに含まれるもの**

| 含まれる | 含まれない |
|---|---|
| `client_id` の値 | `code` の文字列 |
| `used` の値 | `expires_at` の値 |
| 実テーブルの行ID（ポインタ） | その他のカラムデータ |

---

## 7. まとめ

| 項目 | 内容 |
|---|---|
| **目的** | 「どのクライアントの、未使用コードか」を高速に検索 |
| **仕組み** | B-Tree による階層的な索引構造 |
| **列順の理由** | `client_id` の方がカーディナリティが高く、絞り込み効果が大きい |
| **検索の流れ** | 索引を辿る → ポインタ取得 → 実テーブルへジャンプ |
| **制約** | `WHERE` 句に `client_id` を含めないと索引が使えない |

> 複合インデックスは「地図」です。正しい順序で地図を引けば、目的の場所に最短ルートで到達できます。
