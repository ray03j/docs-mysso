## 1. クラス設計の基本思想

### 1.1 関心の分離（Separation of Concerns）

`idp-user-service` のクラス設計は、以下の 4 つの層に責務を明確に分離することを基本とする。

| 層 | 責務 | 代表クラス |
|---|---|---|
| **モデル** | データの整合性、バリデーション、DB 制約 | `User` |
| **サービス** | ビジネスロジック、外部ライブラリのラップ | `User::PasswordService`, `User::AuthenticationService` |
| **コントローラー** | HTTP リクエストの受信、パラメータ処理、レスポンス返却 | `Api::V1::UsersController`, `Api::V1::Auth::VerifyController` |
| **ルーティング** | URL → コントローラーアクションの対応 | `config/routes.rb` |

**なぜこの分離か**

- 各層が「自分の言語」で語れるようにする。モデルは「データの制約」、サービスは「ビジネスルール」、コントローラーは「HTTP プロトコル」に集中する。
- 変更の影響範囲を局所化する。サービス層のロジックを変更しても、コントローラーのテストが壊れにくい。
- テストの層別設計（テストピラミッド）と対応する。各層の責務が明確であれば、「どのレイヤーで何をテストするか」の判断が容易になる。

### 1.2 単一責任の原則（SRP）

各クラスは「変更理由を 1 つにする」を目指す。ただし、過度に細分化すると「クラスが多すぎて全体像が掴めない」という問題が生じるため、現実的なバランスを取る。

**具体例**

- `User` モデルは「ユーザーデータの整合性」を保証する。認証ロジックは持たない。
- `User::AuthenticationService` は「認証の成否を判定する」。DB へのクエリとパスワード検証を組み合わせる。
- `User::PasswordService` は「bcrypt のハッシュ化と検証」のみを行う。

**トレードオフ**

| メリット | デメリット |
|---|---|
| クラスの目的が明確で、修正時の影響範囲が狭い | クラス数が増え、ファイル構成が複雑になる |
| テストが層ごとに独立し、失敗時の原因特定が容易 | 単純な処理でも「サービスクラスを作る」オーバーヘッドが生じる |
| 再利用性が高まり、他のマイクロサービスでも使い回せる | 小規模機能では「 over-engineering 」に見えることがある |

## 2. サービス層の導入判断

### 2.1 Fat Model vs Service Object

Rails の慣習では「モデルにビジネスロジックを寄せる（Fat Model）」が一般的だが、`idp-user-service` では意図的に Service Object を導入している。

**採用した設計（Service Object）**

```ruby
class User
  class AuthenticationService
    def self.authenticate(email, password)
      user = User.find_by(email: email)
      return nil unless user
      return user if PasswordService.verify?(password, user.password_digest)
      nil
    end
  end
end
```

**トレードオフ**

| Fat Model | Service Object（現行設計） |
|---|---|
| コードが集中し、ファイル数が少ない | クラスが分散し、ディレクトリ構造が増える |
| Rails の慣習に従い、新規開発者が理解しやすい | 独自の命名規則と配置ルールを覚える必要がある |
| モデルが巨大化し、テストが肥大化する | 各サービスの責務が小さく、テストが書きやすい |
| 認証・ハッシュ化・バリデーションが 1 つのクラスに混在する | 認証ロジックを独立させ、`idp-client` など他サービスでも流用しやすい |

**idp-user-service での判断理由**

- **IdP 内部での責務分離と再利用性**：`PasswordService` は `User` モデルに閉じ込めず、独立したサービス層として配置する。これにより、CLI ツールやバッチ処理、将来の別ドメイン（`Client` 等）からも利用しやすくなる。モデルに閉じ込めると、ActiveRecord への依存が伴い再利用が困難になる。
- **テストの独立性**：`User` モデルのテストが「バリデーション + コールバック + 認証ロジック」の混合にならない。
- **変更の局所化**：認証方式を「bcrypt から Argon2 へ変更する」場合、`PasswordService` だけを差し替えればよい。

### 2.2 なぜ `has_secure_password` を使うのか

Rails の `has_secure_password` は bcrypt によるパスワードハッシュ化の標準機能であり、本プロジェクトではこれを採用する。

**採用理由**

- **セキュリティの信頼性**：`has_secure_password` は Rails コア機能として長年の実績とセキュリティレビューを受けている。独自実装では隠れたバグ（タイミング問題による二重ハッシュ化、バリデーションとの競合など）のリスクがある。
- **標準化による認知負荷の低減**：新規開発者が「なぜ標準機能を使わないのか」を学ぶ必要がない。ドキュメントに理由を書く必要がある時点で、標準から外れるコストが発生している。
- **機能の網羅性**：`password` / `password_confirmation` 仮想属性、`presence` バリデーション、認証メソッド `authenticate` を自動提供する。これらを自前で実装するコストを省ける。
- **カスタマイズの両立**：パスワードポリシーの追加や認証方式の変更が必要な場合、`authenticate` メソッドをオーバーライドする、あるいは `PasswordService` を併用することで対応できる。`has_secure_password` を使うこととサービス層への切り出しは排他ではない。

**トレードオフ**

| `has_secure_password` を使う場合（現行設計） | 独自の `PasswordService` に全面委譲する場合 |
|---|---|
| 1 行で導入でき、Rails エコシステムで広く知られている | 実装コードが増え、新規開発者の学習コストが高い |
| Rails のバージョンアップで自動的にセキュリティ改善が入る | セキュリティパッチは自前で適用する必要がある |
| `password_digest` カラム名やメソッド名が規約に従う | カラム名・メソッド名を自由に設計できるが、チーム内での一貫性が失われる |
| ActiveModel への依存はあるが、Rails アプリケーションではこれは避けられない | 純粋な Ruby で実装できたとしても、結局 `User` モデルは ActiveRecord に依存する |

**idp-user-service での判断理由**

- `idp-user-service` は Rails アプリケーションであり、`User` モデルは `ApplicationRecord` を継承している。`has_secure_password` による ActiveModel への依存を問題視するのであれば、Rails 自体を使わない方が一貫性がある。
- パスワード処理をモデルから切り出したい場合、`has_secure_password` と `PasswordService` は併用可能である。例えば `authenticate` メソッドをオーバーライドし、内部で `User::PasswordService.verify?` を呼び出すことで、ハッシュ化方式の一元管理と標準機能の利便性を両立できる。
- `before_validation` による「隠れた副作用」も解消される。`has_secure_password` は内部で適切なタイミングでハッシュ化を行い、`password_digest` の整合性を保つ。

## 3. クラスメソッドによる状態を持たない設計

### 3.1 インスタンス化しない理由

`PasswordService` と `AuthenticationService` は、すべてのメソッドをクラスメソッド（`self.`）として定義している。

```ruby
class User
  class PasswordService
    def self.hash(password)
      BCrypt::Password.create(password)
    end

    def self.verify?(password, password_digest)
      return false if password.blank? || password_digest.blank?
      BCrypt::Password.new(password_digest) == password
    end
  end
end
```

**なぜクラスメソッドか**

- **状態を持たない**：`PasswordService` は「入力されたパスワードをハッシュ化する」「ハッシュと照合する」という純粋関数の集合。インスタンス変数を持つ必要がない。
- **呼び出しのシンプルさ**：`User::PasswordService.hash('pass')` と 1 ステップで呼べる。インスタンス化のための `.new` が不要。
- **副作用の排除**：メソッドの結果は「入力だけで決まる」。同じ入力には常に同じ振る舞い（`hash` はソルトにより異なる文字列を返すが、検証は一貫する）が期待できる。

### 3.2 純粋関数としてのメリットと限界

**トレードオフ**

| メリット | デメリット |
|---|---|
| テストが極めて簡単（入力と出力だけで検証できる） | 状態を持たないため、「認証履歴の記録」「レート制限」などの横断的関心事を実装しにくい |
| スレッドセーフ（インスタンス変数がないため共有されても安全） | 将来的に「設定値（コスト係数）を注入したい」場合、クラスメソッドでは DI が困難 |
| 呼び出し側のコードが短くなる | Ruby では「クラスメソッドのテスト」はインスタンスメソッドと同様に書けるが、一部の開発者にとって「OO 的でない」と感じられる |

**将来の拡張と妥協点**

現時点では「状態を持たない」ことを優先しているが、Phase 2 で「認証失敗回数の記録」「レート制限」が必要になった場合、インスタンス化または別のクラス（`User::AuthenticationAttempt` など）を導入する必要がある。その際は「状態を持つクラス」と「純粋関数のクラス」を分離し、後者は変更しない方針とする。

## 4. ネームスペース設計

### 4.1 `User::` 以下にサービスを配置する理由

サービスクラスは `User::PasswordService`、`User::AuthenticationService` という名前空間の下に配置している。

**なぜこの配置か**

- **関連性の明示**：`PasswordService` が「User ドメインに属する」ことを名前空間で表現する。トップレベルに `PasswordService` を置くと、「これはユーザーのパスワードか、クライアントのパスワードか、あるいは共通ユーティリティか」が曖昧になる。
- **自動読み込みの整合性**：Rails の Zeitwerk では `user/password_service.rb` が `User::PasswordService` に自動マッピングされる。ファイルパスとクラス名が一貫し、保守性が高い。
- **衝突の防止**：トップレベルの `AuthenticationService` は、将来 `idp-auth` サービスにも同じ名前のクラスができる可能性がある。ネームスペースで分離することで、クラス名の衝突を防ぐ。

### 4.2 代替案：トップレベルサービスクラス

**トレードオフ**

| `User::PasswordService`（現行設計） | `PasswordService`（トップレベル） |
|---|---|
| ドメイン境界が明確 | サービス名が短く、タイピングが少ない |
| ディレクトリ構造が深くなる（`app/services/user/`） | ディレクトリが平坦（`app/services/`） |
| 他のドメイン（`Client::PasswordService`）と区別しやすい | ドメインが増えると「どのサービスが何のためか」わかりにくくなる |
| ファイルパスが長くなり、エディターのタブが圧迫する | エディターでの視認性が良い |

**idp-user-service での判断理由**

マイクロサービス内ではドメインの種類が限られる（現時点では `User` のみ）ため、トップレベルでも混乱は生じにくい。ただし、「将来的に `Client::PasswordService` を追加する可能性」を考慮し、あらかじめ `User::` という名前空間を確保しておく。これにより、サービス数が増えても命名の一貫性を保てる。

## 5. コントローラーの責務制限

### 5.1 Thin Controller の実現

コントローラーは「HTTP という外部プロトコルと内部処理の橋渡し」に徹し、ビジネスロジックを含まない。

```ruby
module Api
  module V1
    class UsersController < ApplicationController
      def create
        user = User.new(user_params)
        if user.save
          render json: { id: user.id, email: user.email, name: user.name }, status: :created
        else
          render json: { errors: user.errors.full_messages }, status: :unprocessable_entity
        end
      end

      private

      def user_params
        params.require(:user).permit(:email, :password, :name)
      end
    end
  end
end
```

**なぜ Thin Controller か**

- **テストの分離**：コントローラーのテストは「HTTP ステータスと JSON 構造」を検証する。ビジネスロジックの細かい分岐はサービス層の単体テストに任せる。
- **再利用性の確保**：認証ロジックがコントローラーに書かれると、CLI ツールやバッチ処理から再利用できない。
- **読みやすさ**：コントローラーを開いたときに「このエンドポイントが何を返すか」が一目でわかる。

### 5.2 レスポンス整形の責務

現行の設計では、コントローラー内で JSON レスポンスを直接構築している。

**代替案：Serializer（ActiveModel::Serializer や jbuilder）**

**トレードオフ**

| コントローラー内で直接構築（現行設計） | Serializer を導入する場合 |
|---|---|
| ファイル数が少なく、即座にレスポンス構造がわかる | レスポンス構造が分散し、コントローラーと Serializer の両方を読む必要がある |
| エンドポイントごとに細かい調整が容易 | 共通の Serializer を使うと、「このエンドポイントだけフィールドを減らす」ような調整が困難 |
| シンプルな API では過剰な抽象化を避けられる | 大規模 API では「レスポンス構造の一貫性」を保ちやすい |
| レスポンス構造の変更がコントローラーに直書きされ、変更履歴が追いやすい | 複数のエンドポイントで同じ Serializer を使うと、意図しない変更の影響が波及する |

**idp-user-service での判断理由**

現時点ではエンドポイントが 2 つ（`POST /api/v1/users`、`POST /api/v1/auth/verify`）のみで、レスポンス構造も単純。Serializer ライブラリを導入するコストに見合わない。ただし、エンドポイントが 5 つ以上に増えた場合や、レスポンスにネストされたリレーションが増えた場合は `ActiveModel::Serializer` または独自の Presenter 層の導入を検討する。

## 6. モデルの責務範囲とコールバック

### 6.1 データ整合性の最後の防波堤

`User` モデルは「DB に保存されるデータが常に整合性を保つこと」を最優先の責務とする。

```ruby
class User < ApplicationRecord
  has_secure_password

  validates :email, presence: true, uniqueness: true
  validates :name, presence: true, length: { maximum: 100 }
end
```

**なぜこの責務範囲か**

- **バリデーションの最終確認**：フロントエンドや他サービスでバリデーションが行われていても、モデルが最後の防波堤となる。`email` の `presence` / `uniqueness` や `password_digest` の `presence` は DB 制約と二重化している。
- **`has_secure_password` による保証**：パスワードのハッシュ化は「保存前に必ず行われる」という不変条件。`has_secure_password` はこの処理を標準化し、コントローラーやサービスが「ハッシュ化を忘れる」リスクを排除する。

### 6.2 `has_secure_password` によるハッシュ化の標準化

**トレードオフ**

| `has_secure_password` でハッシュ化（現行設計） | コントローラーまたはサービスでハッシュ化する場合 |
|---|---|
| ハッシュ化を「保存の前提条件」として自動保証できる | コントローラー側でハッシュ化を行うと、将来のエンドポイント追加時に「ハッシュ化を忘れる」リスクが生じる |
| `password_digest` の `presence` バリデーションを自動提供 | 手動で `password_digest` のバリデーションを書く必要がある |
| `update` 時に意図しない再ハッシュ化を防ぐ内部ロジックを持つ | `if: -> { password.present? }` などの自前実装が必要になり、バグの温床になる |
| コールバックの「隠れた副作用」が標準化され、挙動が予測しやすい | 独自の `before_validation` はコールバックチェーンの複雑化を招く |

**idp-user-service での判断理由**

- **一貫性の確保**：`has_secure_password` はどの経路から保存されても、適切なタイミングでハッシュ化を行う。コントローラーやサービス側でハッシュ化を行う場合、エンドポイント追加時に「ハッシュ化を忘れる」リスクが生じる。
- **バリデーションとの整合性**：`password_digest` の存在と、平文パスワードのハッシュ化が自動的に整合する。`before_validation` や `before_save` の順序を手動で調整する必要がない。

**将来のリスク**

`has_secure_password` を使っていても、Phase 2 で「パスワード変更時にメール通知を送る」などの追加処理が必要になった場合、コールバックが増える可能性はある。その際は「コールバックの整理」（例：`User::Callbacks` モジュールへの分離）を検討する。ただし、パスワードハッシュ化自体は標準機能に委ねることで、基本挙動の安定性は維持される。

## 7. DRY 原則と局所化

### 7.1 `PasswordService` への集約

パスワードのハッシュ化は、`User` モデル、`AuthenticationService`、将来的な `Client` モデルなど複数箇所で必要になる。`PasswordService` に集約することで、DRY（Don't Repeat Yourself）を実現している。

```ruby
class User
  class PasswordService
    def self.hash(password)
      BCrypt::Password.create(password)
    end

    def self.verify?(password, password_digest)
      return false if password.blank? || password_digest.blank?
      BCrypt::Password.new(password_digest) == password
    end
  end
end
```

**なぜこの集約か**

- **変更の単一箇所化**：bcrypt のコスト係数を変更したい場合、`PasswordService.hash` の 1 箇所だけを修正すればよい。
- **セキュリティレビューの容易さ**：「パスワードに関する処理はすべて `PasswordService` に集まっている」という構造により、セキュリティ監査時に該当ファイルだけを精査すればよい。

### 7.2 共通化の境界線

**トレードオフ**

| 過度に DRY にする場合 | 適度に重複を許容する場合（現行設計） |
|---|---|
| 共通部分の変更が予期しない箇所に影響を与える | 各クラスが独立して変更可能で、影響範囲が制御しやすい |
| 共通メソッドの引数が増え、汎用性のために複雑化する | コードが若干増えるが、各箇所の意図が明確 |
| ライブラリのように「どこからでも使える」設計になり、依存関係が不明瞭になる | サービス間の依存が明示的で、設計図としての価値が高い |

**idp-user-service での判断理由**

- `PasswordService` は「bcrypt のラッパー」として機能し、ビジネスロジックを含まない。このレベルの共通化は「実装の詳細を隠蔽する」だけで、副作用のリスクは低い。
- ただし、`AuthenticationService` は `User` モデルに強く依存しており、他のドメイン（`Client`）には使えない。このような「ドメイン特化型」の処理は無理に共通化せず、必要に応じて `Client::AuthenticationService` を別途作成する方針とする。

## 8. マイクロサービス特有の設計判断

### 8.1 ステートレス設計

`idp-user` サービスはステートレスな API サービスとして設計されている。セッション管理は `idp-auth` で行い、`idp-user` は「1 リクエストで完結する処理」のみを提供する。

**トレードオフ**

| ステートフル設計 | ステートレス設計（現行設計） |
|---|---|
| セッションを保持できるため、連続したリクエストの処理が高速 | スケールアウトが容易（どのインスタンスでも同じ結果を返せる） |
| セッションストア（Redis 等）が不要な場合もある | 毎回認証情報を送信する必要があるが、内部 API では許容範囲 |
| セッション同期の複雑さが生じ、水平スケールが困難になる | サービス間の責務が明確（`idp-user` は「ユーザー情報の管理」のみ） |

**idp-user-service での判断理由**

- `idp-user` は「他のマイクロサービスから呼ばれる内部 API」であり、クライアントから直接アクセスされない。セッション管理を持ち込むと、サービスの独立性が損なわれる。
- ステートレス設計により、テストも「1 リクエスト単位」で完結し、テスト間の状態汚染が生じにくい。

### 8.2 内部 API としての JSON 契約

`idp-user` は `idp-auth` から呼び出される内部サービスであり、レスポンスの JSON 構造は「契約」である。

```ruby
def success_response(user)
  {
    authenticated: true,
    user: {
      id: user.id,
      email: user.email,
      name: user.name
    }
  }
end
```

**トレードオフ**

| 厳密なスキーマ定義（OpenAPI / JSON Schema） | コードとテストで暗黙的に契約を保つ（現行設計） |
|---|---|
| スキーマ変更時に呼び出し側への影響を自動検出できる | スキーマ定義の管理コストが増える |
| クライアントコードの生成が可能 | 2 サービス（`idp-user`, `idp-auth`）のみでは導入コストに見合わない |
| ドキュメントとしての価値が高い | 現行のリクエストスペックが「手作りの契約テスト」として機能している |

**idp-user-service での判断理由**

現時点ではサービス間の連携が 2 つ（`idp-auth` → `idp-user`）のみで、OpenAPI や Pact のようなツール導入は「オーバーキル」。ただし、Phase 2 でサービス数が増えた場合は「レスポンス構造のスキーマ定義」を導入し、契約の破壊を自動検出する体制を整える。

## 9. まとめ：各設計判断のトレードオフ

以下は `idp-user-service` で行った主要なクラス設計判断と、そのトレードオフをまとめたもの。

| 設計判断 | 採用 | トレードオフの要約 |
|---|---|---|
| **Service Object の導入** | ✅ 採用 | Fat Model を避け、認証ロジックを独立。クラス数は増えるがテストと再利用性が向上 |
| **`has_secure_password` の採用** | ✅ 採用 | Rails 標準のセキュリティ機能を利用し、隠れたバグを回避。実装コストを抑えつつ、必要に応じて `PasswordService` との併用で拡張可能 |
| **クラスメソッド（状態なし）** | ✅ 採用 | 純粋関数としてテストが容易。将来の「状態が必要な拡張」では別クラスが必要になる可能性 |
| **`User::` ネームスペース** | ✅ 採用 | ドメイン境界が明確。ファイルパスが深くなるが、将来的な衝突を防止 |
| **Thin Controller** | ✅ 採用 | HTTP 層とビジネスロジックを分離。シンプルだが、レスポンス整形の責務はコントローラーに残る |
| **Serializer 不使用** | ✅ 現行では採用 | エンドポイント数が少ないためシンプルさを優先。増えたら導入を検討 |
| **`has_secure_password` で標準化** | ✅ 採用 | Rails 標準機能でハッシュ化を保証。自前の `before_validation` コールバックを削減し、バリデーションとの整合性を自動的に保つ |
| **ステートレス設計** | ✅ 採用 | スケールアウトと責務分離のため。セッション管理は `idp-auth` に委譲 |
| **OpenAPI / Pact 不使用** | ⚠️ 現行では見送り | 2 サービス間の連携では手動で十分。サービス数増加時に再評価 |

**最終的な判断基準**

- **「このクラスが変更されたとき、どのくらいの範囲に影響が出るか」** → 影響範囲が狭い設計を選ぶ
- **「このコードを IdP 内部の別ドメインやツールから使い回せるか」** → フレームワーク依存を減らし、純粋な Ruby のみで書く
- **「テストが失敗したとき、どのファイルを開けばよいか」** → 責務が明確で、デバッグの切り分けが容易な設計を選ぶ

現行のクラス設計は、「マイクロサービスの内部 API・認証系バックエンド」という文脈で、これらの基準に対して最もバランスの取れた形として選択している。サービスの規模やフェーズが変われば、一部の判断（Serializer の導入、コントラクトテストの導入）は見直されることを前提としている。
