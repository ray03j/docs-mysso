## 1. 概要

**DB 制約と二重化** とは、アプリケーション層のバリデーションとデータベース層の制約を両方設けることで、データ整合性を多重に担保する設計方針である。

単一の層に依存すると、バリデーションすり抜けや意図しないデータ破損が生じるリスクがある。二重化により「人間向けの親切」と「システム向けの絶対保証」を両立する。

---

## 2. 二重化の具体例

`idp-user-service` の `User` モデルを例に、二重化がどのように機能するかを示す。

### アプリケーション層（モデル）

```ruby
class User < ApplicationRecord
  has_secure_password

  validates :email, presence: true, uniqueness: true
  validates :name, presence: true, length: { maximum: 100 }
end
```

### データベース層（マイグレーション）

```ruby
create_table :users do |t|
  t.string :email, null: false
  t.string :password_digest, null: false
  t.string :name, null: false, limit: 100

  t.timestamps
end

add_index :users, :email, unique: true
```

| 層 | 制約 | 役割 |
|---|---|---|
| **モデル（アプリ層）** | `has_secure_password`、`validates :email, presence: true, uniqueness: true` | ユーザーに即座にフィードバック。フレンドリーなエラーメッセージを返す |
| **DB（永続化層）** | `NOT NULL` 制約、`UNIQUE` インデックス | 最後の防波堤。バリデーションをすり抜けた不正データを物理的に拒否する |

**補足**: `name` は `feature/database-schema` で `null: false` と定義しており、モデル層の `presence: true` とDB層の `NOT NULL` 制約で二重化している。

---

## 3. なぜ二重化するのか

### 3.1 レースコンディション対策

モデルの `uniqueness` バリデーションは「検証時点で重複がないか」を確認するだけである。同時リクエスト時には以下のような競合が起こりうる。

```
リクエスト A: SELECT * FROM users WHERE email = 'foo@example.com' → 0 件
リクエスト B: SELECT * FROM users WHERE email = 'foo@example.com' → 0 件
リクエスト A: INSERT INTO users (email) VALUES ('foo@example.com')
リクエスト B: INSERT INTO users (email) VALUES ('foo@example.com')  ← 重複！
```

モデル層のバリデーションではこの競合を防げない。DB の `UNIQUE` インデックスは排他制御により確実に重複を拒否する。

### 3.2 複数経路からの保存対策

コントローラー以外の経路からもデータは保存される可能性がある。

- バッチ処理・Rake タスク
- Rails コンソールからの直接操作
- 他マイクロサービス経由の直接 DB アクセス
- 将来追加される API エンドポイント

DB 制約があれば、これらの経路からの不正データも物理的に防げる。

### 3.3 防御的設計

| 層の役割 | 性質 |
|---|---|
| **バリデーション** | 「人間向けの親切」。エラーメッセージを返し、UI でフィードバックする |
| **DB 制約** | 「システム向けの絶対保証」。どんな経路から来てもデータ破損を防ぐ |

両方を置くことで、どちらか一方が欠落・バグってもデータ整合性が保たれる。

## 4. トレードオフ

| メリット | デメリット |
|---|---|
| データ整合性が多重に担保される | マイグレーションとモデルの両方をメンテナンスする必要がある |
| レースコンディションや複数経路の保存に強い | スキーマ変更時に両方を同期させるオーバーヘッドが生じる |
| どの層が「真の制約」かが明確（DB が最終決定権を持つ） | DB 制約違反のエラーは Rails の `ActiveRecord::RecordInvalid` より扱いにくい（`ActiveRecord::StatementInvalid` や `PG::UniqueViolation` など） |
| セキュリティ監査時に「どこで何を保証しているか」が明確 | 小規模アプリやプロトタイプでは「過剰な防御」と見られることがある |

**idp-user-service での判断理由**

- 認証系サービスではデータ整合性が最重要。メールアドレスの重複やパスワードハッシュの欠落は許容できない。
- 「モデルバリデーションだけで十分」という楽観的設計を避け、DB 制約を最後の防波堤とする。
- ただし、DB 制約違反のエラーは適切にキャッチし、500 エラーにならないようコントローラー層でハンドリングする。

## 5. idp-user-service での実装

### モデル層

```ruby
class User < ApplicationRecord
  has_secure_password

  validates :email, presence: true, uniqueness: true
  validates :name, presence: true, length: { maximum: 100 }
end
```

### マイグレーション層

```ruby
class CreateUsers < ActiveRecord::Migration[7.1]
  def change
    create_table :users do |t|
      t.string :email, null: false
      t.string :password_digest, null: false
      t.string :name, null: false, limit: 100

      t.timestamps
    end

    add_index :users, :email, unique: true
  end
end
```

### エラーハンドリング（コントローラー層）

DB 制約違反が発生した場合、`ActiveRecord::RecordNotUnique` をキャッチして適切なレスポンスを返す。

```ruby
module Api
  module V1
    class UsersController < ApplicationController
      def create
        user = User.new(user_params)
        user.save!
        render json: { id: user.id, email: user.email, name: user.name }, status: :created
      rescue ActiveRecord::RecordNotUnique
        render json: { errors: ['Email has already been taken'] }, status: :unprocessable_entity
      rescue ActiveRecord::RecordInvalid => e
        render json: { errors: e.record.errors.full_messages }, status: :unprocessable_entity
      end
    end
  end
end
```

**注意点**

- 通常はモデルの `uniqueness` バリデーションが先に発火し、DB 制約違反は起こらない。
- DB 制約違反は「モデルバリデーションをすり抜けた異常系」として扱う。
- レスポンスメッセージはモデルバリデーションと統一感を持たせ、呼び出し側（`idp-auth`）が区別しなくてもよいようにする。

## 6. まとめ

| 項目 | 内容 |
|---|---|
| **定義** | アプリ層のバリデーションと DB 層の制約を両方設け、データ整合性を多重に担保する設計 |
| **目的** | レースコンディション、複数経路からの保存、バリデーションの欠落に対する防御 |
| **トレードオフ** | メンテナンスコスト増 vs データ破損リスク減 |
| **idp-user-service の判断** | 認証系サービスにおいてデータ整合性は最重要なため、二重化を採用。DB 制約違反は異常系として適切にハンドリングする |

**最終的な判断基準**

- **「モデルバリデーションだけで十分か？」** → 同時リクエストやコンソール操作を考慮すると、DB 制約なしでは不十分
- **「DB 制約違反のエラーは適切にハンドリングできているか？」** → 呼び出し側に 500 エラーを返さず、意味のあるエラーメッセージを返す
- **「スキーマ変更時にモデルとマイグレーションの同期を忘れていないか？」** → コードレビューで必ず両方を確認する
