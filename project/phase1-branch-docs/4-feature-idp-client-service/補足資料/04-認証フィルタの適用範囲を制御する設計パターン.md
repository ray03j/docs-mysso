## 背景

`03-内部APIキー認証の仕組み.md` で整理した通り、本プロジェクトは「`ApplicationController` に `before_action` を設置し、`internal_api?` のオーバーライドで適用有無を切り替える」Template Method パターンを採っている。

同じ目的(コントローラ/アクション単位で認証フィルタの適用有無を制御する)を実現する設計パターンは他にもある。本ドキュメントでは、それらをすべて **同じ内部APIキー認証の題材** で書き下して比較する。

題材とする仕様:

- チェック処理: ヘッダ `X-Internal-API-Key` と `ENV['INTERNAL_API_KEY']` の一致を確認し、不一致なら 401
- 保護対象: `VerifyController` は全アクション、`ClientsController` は `show` のみ
- `index` / `create` など管理画面向けアクションは保護しない

なお、各コード例は要点が伝わるよう簡略化したものであり、実装そのものは `idp-client/app/controllers/application_controller.rb` を参照。

## 比較表

| パターン | 適用判定の場所 | 追加ファイル | メリット | デメリット | 向いている場面 |
|---|---|---|---|---|---|
| 1. Template Method | 各コントローラのフックメソッド | なし | 親に骨格を集約しつつ子が差し替え可能。追加ファイル不要 | 判定ロジックが複雑化するとフックが増殖する | 条件が単純で、継承階層が1段の構成 |
| 2. only: / skip_before_action | 各コントローラの宣言行 | なし | Rails 標準の最も素直な書き方。アクション単位の指定が明示的 | 保護が「宣言し忘れ」に依存。opt-in の抜け漏れリスク | アクション単位の指定が中心の小規模API |
| 3. 専用基底クラス | 継承元の選択 | 基底クラス1つ | 継承関係だけで保護が分かる。間違った親を継承しなければ漏れない | 「show のみ保護」のようなアクション混在が表現しにくい | コントローラ単位で丸ごと内部/公開が分かれる |
| 4. Concern | `include` 宣言 | Concern 1つ | チェック処理と宣言をモジュールに閉じ込められる。複数の認証種別を積み増せる | 継承と mixin の2経路で挙動を追う必要がある | 認証パターンが複数種類ある、または増える見込み |
| 5. ルーティング / ミドルウェア | routes.rb / middleware | 制約 or ミドルウェア1つ | コントローラに到達する前に遮断。認証がアプリコードから分離 | 制約不一致は 404 になり 401 を返すには別途工夫が必要。アクション単位の制御は苦手 | パス単位の保護、ゲートウェイ的な前段処理 |
| 6. ポリシーレジストリ | 設定テーブル | なし(定数追加のみ) | 保護対象が1か所に一覧でき、監査しやすい | コントローラを読むだけでは保護有無が分からない間接参照 | 対象が多く、一覧性・監査性が重要 |

## 使い分けの目安

- 保護が「コントローラ丸ごと」に揃っている → 3 / 4
- 「show のみ」などアクション単位の混在が多い → 1 / 2
- 認証の種類(内部APIキー、JWT、…)が複数ある・増えそう → 4
- パス単位で前段遮断したい、認証をアプリから分離したい → 5
- 保護対象の一覧を構成管理的に見たい → 6
- 小規模で条件が1種類だけ → 1 で十分

## パターン一覧(コード例)

### 1. Template Method パターン(本プロジェクトの採用例)

**仕組み**: 親クラスが `before_action` の登録と判定用フックメソッド(デフォルト `false`)を定義し、子クラスはフックのオーバーライドだけで適用を有効化する。

親(雛形):

```ruby
class ApplicationController < ActionController::API
  before_action :require_internal_api_key, if: :internal_api?

  private

  def internal_api?
    false
  end
end
```

子(有効化スイッチ):

```ruby
class Api::V1::VerifyController < ApplicationController
  private

  def internal_api?
    true
  end
end

class Api::V1::ClientsController < ApplicationController
  private

  def internal_api?
    action_name == 'show'
  end
end
```

**読みどころ**:

- 「適用するかどうか」が各コントローラのメソッドとして読めるため、アクション単位の条件(`action_name == 'show'`)も自然に書ける
- 親子1段の継承だけで完結し、追加ファイルが要らない
- 一方で「子が任意の Ruby コードを書ける」自由度があるため、判定条件が複雑化するとコントローラごとの実装差異が生まれやすい

### 2. `only:` / `skip_before_action` による宣言的指定

**仕組み**: 親にはチェック処理だけを置き、フィルタの登録自体は各コントローラが `only:` 付きで宣言する(opt-in)。逆に親で全登録して子が `skip_before_action` する(opt-out)形も取れる。

```ruby
class ApplicationController < ActionController::API
  private

  def require_internal_api_key
    # ... 共通のチェック処理
  end
end

class Api::V1::VerifyController < ApplicationController
  before_action :require_internal_api_key # 全アクション
end

class Api::V1::ClientsController < ApplicationController
  before_action :require_internal_api_key, only: :show
end
```

**読みどころ**:

- Rails 標準機能だけで書ける最も素直な形。`only: :show` が宣言行に直に現れる
- opt-in なので「新しい内部コントローラを足して宣言を忘れる」と無防備なまま公開される。Template Method も同じリスクを持つが、こちらは判定用フックすら存在しない分、抜け漏れに気づきにくい
- opt-out(親で登録 + `skip_before_action`)は漏れに強いが、「公開したい側が毎回 skip を書く」ことになり管理画面系アクションが多い構成では煩雑

### 3. 専用基底クラスの継承

**仕組み**: 内部API専用の基底クラスを用意し、保護したいコントローラはそこから継承する。「どの親を継承するか」自体が保護の宣言になる。

```ruby
class ApplicationController < ActionController::API
end

class InternalApiController < ApplicationController
  before_action :require_internal_api_key

  private

  def require_internal_api_key
    # ... 共通のチェック処理
  end
end

class Api::V1::VerifyController < InternalApiController
end # 全アクション保護

class Api::V1::ClientsController < ApplicationController
  before_action :require_internal_api_key, only: :show # 混在分は別途宣言が必要
end
```

**読みどころ**:

- 「内部APIかどうか」が継承関係という構造情報になるため、ファイルを開いて1行目で分かる
- `InternalApiController` に共通の内部向け振る舞い(監査ログ等)を載せる拠点にもなる
- ただし「コントローラ丸ごと保護」が前提。`ClientsController` のように保護/非保護が混在するコントローラは表現に無理が出る(結局 2 の併用になる)

### 4. Concern による opt-in

**仕組み**: チェック処理と `before_action` 登録を Concern にまとめ、必要なコントローラが `include` する。認証の種類ごとに Concern を分けられる。

```ruby
module InternalApiAuthenticatable
  extend ActiveSupport::Concern

  included do
    before_action :require_internal_api_key
  end

  private

  def require_internal_api_key
    # ... 共通のチェック処理
  end
end

class Api::V1::VerifyController < ApplicationController
  include InternalApiAuthenticatable
end
```

**読みどころ**:

- 認証ロジックが `ApplicationController` から分離され、認証方式の追加(例: `AdminAuthenticatable`)がモジュールの追加で済む
- 「include していれば保護される」という1種類の読み方だけ追えばよい
- 継承(コントローラ階層)と mixin(認証)の2系統を読み分ける必要があり、小規模構成ではファイル数・概念数の割に見返りが少ない

### 5. ルーティング / ミドルウェアでの保護

**仕組み**: コントローラに到達する前の層で遮断する。Rails のルーティング制約、または Rack ミドルウェアを使う。

ルーティング制約の例:

```ruby
class InternalApiConstraint
  def matches?(request)
    request.headers['X-Internal-API-Key'] == ENV.fetch('INTERNAL_API_KEY')
  end
end

Rails.application.routes.draw do
  namespace :api do
    namespace :v1 do
      constraints InternalApiConstraint.new do
        post 'clients/verify', to: 'verify#create'
      end
      resources :clients, only: %i[create index show]
    end
  end
end
```

**読みどころ**:

- 保護の判定がリクエストパスに基づくため、コントローラ側は認証を一切意識しない
- 制約に合わないリクエストはルーティング不成立 = **404** になる。「存在を隠す」意味では有効だが、401 を返したい場合は Rack ミドルウェア側で自前にレスポンスを組み立てる必要がある
- `show` だけ保護のようなアクション単位の制御は、パス設計(`/api/v1/internal/...` のように分ける)とセットでないと表現できない

### 6. ポリシーレジストリの参照

**仕組み**: 「どのコントローラのどのアクションが保護対象か」を設定テーブル(定数や設定ファイル)に集約し、単一の `before_action` がそれを参照して判定する。

```ruby
INTERNAL_API_POLICY = {
  'Api::V1::VerifyController' => :all,
  'Api::V1::ClientsController' => %i[show]
}.freeze

class ApplicationController < ActionController::API
  before_action :require_internal_api_key, if: :internal_api_required?

  private

  def internal_api_required?
    rule = INTERNAL_API_POLICY[self.class.name]
    rule == :all || Array(rule).map(&:to_sym).include?(action_name.to_sym)
  end
end
```

**読みどころ**:

- 保護対象の全体像が1ファイルに一覧でき、「このAPIで守られているエンドポイントはどれか」を監査しやすい
- 判定が Ruby コードではなくデータになるため、外部設定化(YAML 等)への発展も素直
- ただしコントローラ単体を読んでも保護の有無が分からない間接参照になり、規模が小さいうちは「一覧するほどの対象がない」ため過剰

## 本プロジェクトでの選択と根拠

採用: **1. Template Method パターン**。選定の連鎖は以下の通り。

1. `VerifyController`(全アクション保護)と `ClientsController#show`(1アクションのみ保護)が混在する
   → 3(専用基底クラス)はコントローラ単位が前提なので、`show` のみ保護を素直に表現できず脱落
2. 判定条件は「常に `true`」か「`action_name` を見る」程度で、外部設定化するほど対象が多くない
   → 6(レジストリ)は一覧性の見返りがなく脱落
3. パス設計を内部向けに分ける予定はなく、401 を返す API 契約もある
   → 5(ルーティング制約)は 404 化と契約の不整合があり脱落
4. Phase 1 の認証方式は内部APIキーの1種類のみ
   → 4(Concern)は分離の見返りがファイル数に見合わず脱落
5. 残る 1 と 2 の比較では、2 は親にフィルタ登録がなく「宣言忘れ = 無防備」の検知手段がない。1 は `internal_api?` というフックの存在自体が「この判断を各コントローラで行うこと」を型として示せる
   → 1 が最も素直

つまりこの設計は「アクション単位の混在」と「小規模構成」の2条件に依存しており、将来「丸ごと保護の内部コントローラ」が多数派になったら 3 または 4 への移行が正当化される。
