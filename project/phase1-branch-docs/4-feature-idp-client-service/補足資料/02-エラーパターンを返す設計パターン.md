## 背景

`ClientVerificationService.verify` は「例外を投げず、常に `{ valid:, client: / error: }` という結果ハッシュを返す」設計を採っている(根拠: `phase1-branch-docs/4-feature-idp-client-service/03_feature-idp-client-service-verify/feature.md` の「戻り値」)。

この設計の動機の大半は「**どう失敗したか(エラーパターン)を潰さずに呼び出し側へ届ける**」ことにある。本ドキュメントでは、同じ目的でよく使われる設計パターンを、すべて **同じクライアント検証の題材** で書き下して比較する。

題材とする仕様:

- 入力: `client_id`、`client_secret`
- 失敗: `client not found` / `invalid client_secret`
- 成功: 検証済みの `Client` を返す
- 呼び出し側: コントローラで 200 / 401 に変換する

なお、各コード例は要点が伝わるよう簡略化したものであり、入力チェックや `redirect_uri` 検証は省いている。実装そのものは `idp-client/app/services/client_verification_service.rb` を参照。

## 比較表

| パターン | 失敗理由を運べる | 成否判定の明示性 | 追加依存 | メリット | デメリット | 向いている場面 |
|---|---|---|---|---|---|---|
| 1. フラグ付き結果ハッシュ | ○(文字列) | ○ | なし | 成否判定が `result[:valid]` 一つ。戻り値と API レスポンスの形を揃えられる | キーは規約でしかなくタイポに弱い。成功/失敗で格納キーが変わり型検査が効かない | サービス層の成否を API 応答に直通させたい |
| 2. 値 or nil | × | △ | なし | 最も単純。`if client = ...` と書ける | 失敗理由が消える。「not found」と「secret 不一致」を区別できない | 失敗が1種類しかない参照系 |
| 3. 例外 | ○(例外クラス) | ○ | なし | 正常系が平坦になる。戻り値チェック忘れが起きない | 頻繁に起きる失敗を例外で制御するとフローが追いにくい。rescue 箇所の設計が必要 | 失敗が本当に例外的 / フレームワークの rescue 機構がある |
| 4. タプル | ○ | ○ | なし | 値とエラーが別スロットで混ざらない | Ruby では多数派でなく、返却順の規約を読み手と共有する必要がある | Go など言語慣習がある環境 |
| 5. Result 型 | ○(型付き) | ◎ | あり(gem) | 成否が型で表現されパターンマッチの網羅性を検査できる。処理を合成できる | gem 導入とチームの習熟が必要。小規模では過剰 | 大規模・複雑な分岐合成、網羅性を保証したい |
| 6. boolean + errors | ○(複数) | ○ | なし(Rails標準) | 複数エラーを同時保持できる。Rails の View 連携が揃っている | 戻り値と理由が別経路。オブジェクトごと渡す必要があり検証用途には重い | フォーム入力など複数エラーの同時表示 |

## 使い分けの目安

- 失敗の種類を呼び出し側が知る必要がある → 1 / 3 / 5
- 失敗が「存在しない」の1種類だけ → 2 で十分
- フレームワークが例外ハンドリングを提供(Rails の `rescue_from`)し、失敗が稀 → 3
- チームが関数型スタイルに習熟し、分岐の網羅性を型で保証したい → 5
- 入力フォームで項目ごとに複数エラーを出す → 6(Rails 標準に乗る)

## パターン一覧(コード例)

### 1. フラグ付き結果ハッシュ(本プロジェクトの採用例)

**仕組み**: 戻り値を必ず Hash にし、`:valid` を成否フラグとする。成功時は `:client`、失敗時は `:error` を添え、呼び出し側はまずフラグだけで分岐し、その後に該当キーを取り出す。

```text
成功: { valid: true,  client: <Client> }
失敗: { valid: false, error: 'invalid client_secret' }
```

サービス側:

```ruby
def self.verify(client_id:, client_secret:)
  client = Client.find_by(client_id: client_id)
  return { valid: false, error: 'client not found' } unless client
  return { valid: false, error: 'invalid client_secret' } unless client.client_secret_valid?(client_secret)

  { valid: true, client: client }
end
```

呼び出し側:

```ruby
result = ClientVerificationService.verify(client_id: params[:client_id], client_secret: params[:client_secret])

if result[:valid]
  render json: verify_response(result[:client])
else
  # 失敗ハッシュが 401 レスポンスのボディと同形なので、そのまま流せる
  render json: { valid: false, error: result[:error] }, status: :unauthorized
end
```

**読みどころ**:

- 失敗理由が `:error` に文字列で乗るので、ログにも API レスポンスにもそのまま使える
- サービスの戻り値と API レスポンスの形を揃えられるため、コントローラは「変換」ではなく「受け渡し」で済む
- 一方で「どのキーが入っているか」は規約でしかない。`result[:cleint]` と typo しても nil が返るだけで気づけないのが弱点

### 2. 成功時は値・失敗時は nil

**仕組み**: 失敗を「値がないこと」で表す。失敗の理由は返却の境界で捨てる。

サービス側:

```ruby
def self.verify(client_id:, client_secret:)
  client = Client.find_by(client_id: client_id)
  return unless client&.client_secret_valid?(client_secret)

  client
end
```

呼び出し側:

```ruby
if client = ClientVerificationService.verify(...)
  render json: verify_response(client)
else
  # なぜ失敗したか分からないので、一律のメッセージしか返せない
  render json: { valid: false, error: 'invalid client credentials' }, status: :unauthorized
end
```

**読みどころ**:

- 最も単純で、Ruby らしく `if client = ...` と書ける
- ただし「not found」と「secret 不一致」は呼び出し側から区別不能。失敗が複数種類ある処理では情報が足りなくなる
- `Client.find_by` 自身がこのパターン。「見つからない」が唯一の失敗ならこれで十分

### 3. 例外を投げる

**仕組み**: 失敗を例外として投げ、メソッドが正常に返った場合の戻り値は常に「成功した値」とする。呼び出し側(またはフレームワーク)が rescue で受け止める。

サービス側:

```ruby
class ClientVerificationService
  class VerificationError < StandardError; end

  def self.verify!(client_id:, client_secret:)
    client = Client.find_by(client_id: client_id)
    raise VerificationError, 'client not found' unless client
    raise VerificationError, 'invalid client_secret' unless client.client_secret_valid?(client_secret)

    client
  end
end
```

呼び出し側(Rails なら `rescue_from` で集約):

```ruby
rescue_from ClientVerificationService::VerificationError, with: :render_unauthorized

def create
  client = ClientVerificationService.verify!(...) # 失敗すればここで例外。以降は実行されない
  render json: verify_response(client)
end

private

def render_unauthorized(exception)
  render json: { valid: false, error: exception.message }, status: :unauthorized
end
```

**読みどころ**:

- 正常系が平坦になり、戻り値チェックの書き忘れが起きない(忘れると例外がそのまま飛ぶ = フェイルファスト)
- 失敗理由は例外クラスや `message` に乗る。クラスを理由別に分ければ、rescue 側で理由ごとの振り分けもできる
- ただし認証失敗のような「普通に起きる結果」を例外で制御すると、処理がジャンプして追いにくい。「本当に例外的な失敗」(DB 接続断など)に使うのが本意

### 4. タプル(値とエラーのペア)を返す

**仕組み**: 常に `[値, エラー]` の2要素を返す。成功時はエラーが nil、失敗時は値が nil。Go 言語の標準慣習を Ruby に持ち込んだ形。

サービス側:

```ruby
# 成功: [client, nil] / 失敗: [nil, error]
def self.verify(client_id:, client_secret:)
  client = Client.find_by(client_id: client_id)
  return [nil, 'client not found'] unless client
  return [nil, 'invalid client_secret'] unless client.client_secret_valid?(client_secret)

  [client, nil]
end
```

呼び出し側:

```ruby
client, error = ClientVerificationService.verify(...)

if error
  render json: { valid: false, error: error }, status: :unauthorized
else
  render json: verify_response(client)
end
```

**読みどころ**:

- 値とエラーが別スロットなので、成功結果にエラーが混ざることがない
- 判定は `if error` とエラー側を見るのが Go 流。「値が nil でも有効な成功」がありうる場面でも安全
- Ruby ではこの流儀が少数派のため、「第1要素が値・第2要素がエラー」という順序の規約をチームで共有する必要がある

### 5. Result 型(モナド)

**仕組み**: 成功を `Success(値)`、失敗を `Failure(理由)` というラッパーオブジェクトで包む。中身の取り出しにパターンマッチや `bind` を経由させることで、成否の扱い忘れを構造的に防ぐ。`dry-monads` gem を使う例。

サービス側:

```ruby
class ClientVerificationService
  include Dry::Monads[:result]

  def self.verify(client_id:, client_secret:)
    client = Client.find_by(client_id: client_id)
    return Failure(:client_not_found) unless client
    return Failure(:invalid_client_secret) unless client.client_secret_valid?(client_secret)

    Success(client)
  end
end
```

呼び出し側(Ruby 3 のパターンマッチ):

```ruby
case ClientVerificationService.verify(...)
in Dry::Monads::Success(client)
  render json: verify_response(client)
in Dry::Monads::Failure(reason)
  render json: { valid: false, error: reason }, status: :unauthorized
end
```

**読みどころ**:

- 成否が「型」として表現されるので、case-in の網羅性チェックが効き、分岐漏れを機械的に検出できる
- `bind` を使えば「成功したら次の処理へ」を合成できる(鉄道指向プログラミング)。失敗した時点で以降はスキップされる
- 失敗理由を Symbol や専用オブジェクトで表現でき、文字列比較に頼らない
- そのぶん gem 導入とチームの習熟が前提。Phase 1 規模のサービスでは過剰になりやすい

### 6. boolean + errors オブジェクト

**仕組み**: メソッドは boolean だけを返し、失敗理由はオブジェクト内部の `errors` に蓄積する。`user.save` → `user.errors` と同じ、Rails で最も馴染みのある形。

サービス側:

```ruby
class ClientVerification
  include ActiveModel::Model

  attr_accessor :client_id, :client_secret
  attr_reader :client

  def verify
    @client = Client.find_by(client_id: client_id)
    return errors.add(:client_id, 'not found') && false unless @client
    return errors.add(:client_secret, 'is invalid') && false unless @client.client_secret_valid?(client_secret)

    true
  end
end
```

呼び出し側:

```ruby
verification = ClientVerification.new(client_id: params[:client_id], client_secret: params[:client_secret])

if verification.verify
  render json: verify_response(verification.client)
else
  render json: { valid: false, errors: verification.errors.full_messages }, status: :unauthorized
end
```

**読みどころ**:

- 「成否(戻り値)」と「理由(オブジェクト内部状態)」が別経路。理由を運ぶにはオブジェクトごと受け渡す必要がある
- 複数エラーの同時保持が本領。「全項目の問題を一括表示」したいフォーム入力のような場面で強い
- 1回の成否だけを知りたい検証用途には、オブジェクト生成と状態の持ち回りがやや重い

## 本プロジェクトでの選択と根拠

採用: **1. フラグ付き結果ハッシュ**。選定の連鎖は以下の通り。

1. 401 レスポンスのボディに `error` を載せる API 契約がある(feature.md / spec.md)
   → 2(値 or nil)は理由を運べないので脱落
2. 認証失敗は「異常」ではなく通常起こりうる結果
   → 3(例外)は制御フローとして不自然なので脱落
3. Phase 1 の小規模サービスに dry-monads は過剰
   → 5 は脱落
4. サービス層の戻り値と API レスポンスの形 `{ valid:, error: }` を揃えると、コントローラが「変換」ではなく「受け渡し」で済む
   → 1 が最も素直

つまりこの設計は「エラーパターンを残す方針」とセットであり、将来エラーメッセージを `invalid_client` 等に統一する(列挙攻撃対策)なら、2 への単純化も正当化される。
