## はじめに

このドキュメントは、`feature/database-schema/idp-auth` ブランチで作成する4つのマイグレーションファイルを、**Rails（ActiveRecord）のマイグレーションが初めての人**にもわかるように解説したものです。

「なぜこのカラムを追加したのか」「このオプションは何をしているのか」を、**「全ファイル共通の大きな構造」**と**「ファイルごとの独自ポイント」**に分けて説明します。

---

## 1. 全ファイルに共通する「大きな構造」

4つのマイグレーションファイルは、すべて以下の同じ骨組みで書かれています。

```ruby
class 何かを作成する < ActiveRecord::Migration[7.1]
  def change
    create_table :テーブル名 do |t|
      # カラム定義...
      t.timestamps
    end

    add_index :テーブル名, :カラム名, unique: true
  end
end
```

### 1.1 `class ... < ActiveRecord::Migration[7.1]` の意味

Rails の「データベース変更手順書」としてのクラスです。  
`ActiveRecord::Migration[7.1]` を継承することで、「このファイルは Rails 7.1 形式のマイグレーションです」と Rails に伝えています。

### 1.2 `def change` の役割

データベースに**変更を加える内容**を書くメソッドです。  
`change` を使うと、Rails が自動的に「元に戻す手順（`down`）」も作ってくれるため、開発者は `create_table` などの「順方向」の処理だけを書けば済みます。

### 1.3 `create_table` でテーブルを作る

`create_table :authorization_codes do |t|` は、「`authorization_codes` という名前のテーブルを作ります」という意味です。  
ブロック変数 `t` を使って、テーブル内のカラムを次々と定義していきます。

### 1.4 `t.型 :カラム名` でカラムを定義する

カラムは「データの入れ物」です。型（データの種類）を指定して作ります。

| 型 | 用途 | 例 |
|---|---|---|
| `t.string` | 短い文字列 | トークン文字列、ID |
| `t.datetime` | 日時 | 有効期限 |
| `t.boolean` | true / false | 使用済みフラグ |

### 1.5 カラムのオプション

カラム定義の横に書くオプションで、データのルールを厳しくしています。

| オプション | 意味 |
|---|---|
| `null: false` | **必須項目**。NULL（空っぽ）を許可しない |
| `default: 値` | 値を指定しなかったときの**デフォルト値** |

### 1.6 `t.timestamps` の役割

すべてのマイグレーションに必ず書かれています。これを書くと、自動的に以下の2つのカラムが追加されます。

- `created_at`：レコードが作られた日時
- `updated_at`：レコードが最後に更新された日時

「いつ作られたのか」「いつ更新されたのか」を Rails が自動で記録してくれます。

### 1.7 `add_index` で検索を速くする

テーブルが大きくなると、データの探し出しが遅くなります。`add_index` は「索引（しらべもの）」を貼る命令です。

```ruby
add_index :テーブル名, :カラム名
```

さらに `unique: true` を付けると、「このカラムの値は重複してはいけない」という**一意性制約**も同時に設けられます。

## 2. 4つのテーブルが持つ「共通の設計思想」

`authorization_codes`、`access_tokens`、`refresh_tokens`、`consents` は、それぞれ別の役割を持ちますが、以下の**共通ルール**で設計されています。

### 2.1 `user_id` / `client_id` は `string` 型で必須

```ruby
t.string :user_id, null: false
t.string :client_id, null: false
```

通常、Rails では「他のテーブルのIDを参照する」場合に `references` 型や整数型を使いますが、今回は **マイクロサービス間でデータベースを分離**しているため、外部キー制約は使えません。  
その代わり、`string` 型で他サービスの ID をそのまま文字列として保持し、サービス間通信で整合性を担保します。

#### 他の選択肢

| 方式 | 概要 | トレードオフ |
|---|---|---|
| **UUID/GUID 型を使う** | `string` の代わりに `uuid` 型を使い、一意性を数学的に高める | 外部キー制約が使えるわけではない。DB によっては専用型の方がインデックス効率が良い場合もある |
| **API Gateway / BFF で事前検証** | 書き込み前に Gateway 層で対向サービスの API を叩き、ID の存在を確認してから書き込む | レイテンシ増加、Gateway の可用性がボトルネックになる。IDp 自身が ID の真贋を担保すべき場面では不自然 |
| **イベント駆動の非同期整合** | 対向サービスの変更イベントを購読し、ローカルにキャッシュまたはミラーテーブルを持つ | 最終的整合性（一時的に不整合が許容される）。CQRS や Saga パターンを伴う場合、実装・運用コストが高い |
| **共有リードレプリカを参照** | 対向サービスの DB リードレプリカに直接接続し、存在チェックだけは外部キーに近い形で行う | ネットワーク分離の原則が崩れる。書き込みはできないので「参照整合性の完全保証」にはならない |
| **gRPC/HTTP で同期的存在確認** | レコード作成・更新時に都度、対向サービスの API を呼び出して ID を検証する | 可用性が連動する（対向サービスが落ちると書き込みも失敗）。今回はこの方式に近いが、呼び出し元の責務とタイミングは設計次第 |

> 本プロジェクトでは「シンプルさ」と「可用性の分離」を優先し、**文字列保持＋サービス間通信で整合性を担保する**方式を採用しています。  
> 上記の選択肢は、将来的にトランザクション量や整合性要件が変わった際の検討材料として参照してください。

#### なぜこの方式がマイクロサービスでは「普通」か

この設計が業界で標準的とされる根拠は3つあります。

| 根拠 | 説明 |
|---|---|
| **Database per Service** | マイクロサービスの基本原則である「1サービス 1データベース」では、他サービスのテーブルに直接外部キーを貼ることは物理的に不可能です。外部キーなしは必然であり、避ける設計は例外です。 |
| **分散システムでは連番IDが使えない** | 整数型の連番は、サービス間で重複したり、マージ・再構成が困難になったりします。中央集権的な採番器が必要となり、サービスの独立性を損ないます。そのため **UUID/ULID を `string` や `uuid` 型で保持する**のが主流です。 |
| **整合性はアプリケーション層で担保する** | 分散システムでサービス間の強い整合性（ACID）を担保することは現実的ではありません。代わりに、gRPC/HTTP による同期的検証、Saga パターンによる補償トランザクション、イベント駆動による最終的整合性のいずれかで管理するのが一般的です。 |

Netflix、Amazon、Uber などの大規模マイクロサービスでも、サービス間の参照整合性はアプリケーションコードや非同期イベントで管理しています。

#### この設計のデメリットと注意点

「文字列保持＋サービス間通信」は標準的ですが、以下のトレードオフを理解して運用する必要があります。

| デメリット / 注意点 | 詳細 | 対策の例 |
|---|---|---|
| **可用性の連動** | 対向サービスが停止・遅延すると、ID の存在確認ができず、書き込みや応答が失敗する可能性があります。 | タイムアウトを短く設定し、サーキットブレーカーで連鎖故障を防ぐ。確認を非同期化し、可用性と整合性を切り分ける。 |
| **参照整合性の緩さ** | 外部キー制約がないため、対向サービスで削除された ID がローカル DB に残り、「ゴミデータ」や「幽霊参照」になるリスクがあります。 | 定期的なクリーンアップジョブを実行。削除イベントを購読してローカルデータも同期削除する。 |
| **デバッグの複雑さ** | データ不整合が起きた際、どのサービスのどの処理が原因かを特定するのが困難です。 | 分散トレーシング（OpenTelemetry など）を導入し、リクエスト ID をサービス間で引き継ぐ。 |
| **レイテンシ増大** | 都度の存在確認により、レスポンス時間が伸び、スループットが低下する可能性があります。 | 検証結果を短時間キャッシュする。書き込み時のみ厳密に検証し、読み出し時は緩やかにする。 |
| **冪等性の確保** | ネットワーク不安定下で同じリクエストが重複すると、重複書き込みや二重検証が発生する可能性があります。 | クライアント生成の冪等キー（idempotency-key）を受け付け、処理の重複実行を防ぐ。 |
| **監視・可観測性** | 不整合の発生に気づきにくく、事后に影響範囲を特定するのが難しいです。 | 整合性チェック用の監視クエリを定期的に実行。整合性率をメトリクス化し、アラートを設定する。 |

> **まとめ**  
> この方式はマイクロサービスでは**普通であり、推奨される設計**ですが、「外部キーに頼らない」ということは**アプリケーション側で整合性の責任を引き受ける**ということです。運用初期から可観測性とクリーンアップ戦略を整えておくことが重要です。

#### 同一DB（共有データベース）方式とのトレードオフ

マイクロサービスでも「複数サービスで1つのDBを共有し、外部キー制約を活かす」という方式も存在します。本プロジェクトが採用した「DB分離＋string保持」との比較は以下の通りです。

| 比較項目 | DB分離＋string保持（本プロジェクト） | 同一DB＋外部キー（共有DB方式） |
|---|---|---|
| **データ整合性** | アプリケーション層で担保。人為的ミスや考慮漏れにより不整合が生じうる | DB レベルで強制。参照整合性は機械的に保証される |
| **サービス独立性** | 高い。各サービスが独自のスキーマ変更・スケーリング・技術選定が可能 | 低い。スキーマ変更は他サービスにも影響。DB のボトルネックが全体に波及 |
| **可用性・耐障害性** | 片方のDB停止がもう片方に直接影響しない | 共有DBが単一障害点（SPOF）になりやすい |
| **パフォーマンス** | サービス間通信のオーバーヘッドあり。ネットワーク遅延が発生する | 同一DB内のJOINや外部キー検査は高速。通信オーバーヘッドなし |
| **運用・監視** | サービス間の不整合を監視する仕組みが別途必要 | DB の監視・バックアップが一元化でき、運用はシンプル |
| **チーム間の結合度** | 低い。チーム間でDBスキーマの調整が不要 | 高い。スキーマ変更の際、他チームとの調整・同期リリースが必要になりやすい |
| **移行・リプレースの容易さ** | サービスごとに独立して移行・リプレース可能 | 共有DBに依存しているため、切り出しや移行が困難 |

> **本プロジェクトでDB分離を選んだ理由**  
> IdP（認証）サービスは他のビジネスドメイン（例: ユーザー管理、クライアント管理）と**ライフサイクルが異なり、可用性要求が特に高い**ため、結合度を下げて独立した運用・スケーリングを可能にする方が長期的に有利です。  
> ただし、サービス数が少なくチームも小規模な初期段階では「同一DB＋外部キー」の方が開発速度は速いため、**組織の規模とドメイン境界の明確さ**が選定の重要な判断材料になります。

### 2.2 トークン・コード系は「重複禁止＋必須」

`authorization_codes` の `code`、`access_tokens` / `refresh_tokens` の `token` は、すべて以下の2つを満たしています。

1. `null: false`（必須）
2. `add_index ..., unique: true`（重複禁止）

認可コードやトークンは**1人に対して1つの値**が割り当てられるランダムな文字列であるため、絶対に重複してはいけません。

### 2.3 `scope` は文字列で保持

OIDC（OpenID Connect）では「どの情報を提供するか」をスコープ（例: `openid profile`）で指定します。これは可変長の文字列なので、`t.string` で保存しています。

### 2.4 `timestamps` はすべてのテーブルに入る

どのテーブルにも `t.timestamps` があり、レコードの作成日時・更新日時を追跡できます。これは「いつデータが生まれたのか」を知る上で必須の情報です。

## 3. ファイルごとの「独自ポイント」

共通の設計思想を押さえた上で、各ファイルが**特別に設定している点**だけを抜き出しています。

### 3.1 `001_create_authorization_codes.rb`

```ruby
t.string :redirect_uri
t.boolean :used, default: false, null: false
```

| 設定 | 意味 |
|---|---|
| `redirect_uri` | 認可後に戻すURL（認可フローで必要） |
| `used` | **認可コードは1回しか使えない**。使われたら `true` にするフラグ。デフォルトは `false`。これにより「コード再利用攻撃」を防ぎます。 |

**インデックスの独自点：**

```ruby
add_index :authorization_codes, [:client_id, :used]
```

「どのクライアントの、未使用コードか」を高速で探すための**複合インデックス**です。

#### 複合インデックスとは？

検索条件が「1つのカラムだけ」ではなく、「複数のカラムを同時に指定する」場合があります。
そのときに複数のカラムをまとめて索引にするのが **複合インデックス（composite index）** です。

```ruby
add_index :テーブル名, [:カラムA, :カラムB]
```

| メリット | 説明 |
|---|---|
| **複数条件の検索が速くなる** | `WHERE カラムA = ? AND カラムB = ?` のような検索が、索引を1回辿るだけで済みます。 |
| **並べ替えも効率化** | 指定した順序（`カラムA → カラムB`）で `ORDER BY` すると、索引の順序をそのまま使えます。 |

> **順序は重要です**  
> 複合インデックスは「左端のカラムから順に」しか効果を発揮しません。  
> 例：`[:client_id, :used]` に対して `WHERE used = ?` だけの検索は、この索引を使えません。  
> 必ず `WHERE client_id = ?`（または `client_id` と `used` の両方）を含めるようにクエリを書きます。

### 3.2 `002_create_access_tokens.rb`

```ruby
t.datetime :expires_at, null: false
```

アクセストークンは短時間（例: 15分）で失効する必要があるため、**有効期限は必須**です。

**インデックスの独自点：**

```ruby
add_index :access_tokens, [:user_id, :client_id]
```

「あるユーザーが、あるクライアントに対して持っているトークン」を探すための複合インデックスです。ログアウト時の「そのユーザーのトークンを全部削除」にも使われます。

### 3.3 `003_create_refresh_tokens.rb`

```ruby
t.datetime :expires_at  # null: false がない！
```

リフレッシュトークンの有効期限は**NULLを許可**しています。  
理由は「トークン回転（rotation）戦略を採用する場合、失効期限を設けずに『使用済みフラグ』で管理する方式もありうる」からです。現時点では将来の方針変更に備えて柔軟性を持たせています。

それ以外のカラム（`token`, `user_id`, `client_id`, `scope`）は `access_tokens` と**まったく同じ理由**で設定されています。

### 3.4 `004_create_consents.rb`

```ruby
t.string :scope, null: false
```

同意（consent）では「何に同意したのか（スコープ）」が必須情報なので、`null: false` を付けています。

**インデックスの独自点：**

```ruby
add_index :consents, [:user_id, :client_id], unique: true
```

「同じユーザー・同じクライアントの同意は1レコードだけ」というルールを作るため、**複合ユニークインデックス**を貼っています。スコープが変わった場合は、その1レコードを更新（UPSERT）します。

## 4. `seeds.rb` について

```ruby
# 開発・テスト環境用の最小データのみ記載
# AuthorizationCode.create!( ... )
```

`seeds.rb` は `rails db:seed` を実行したときに動く「初期データ投入スクリプト」です。

認可コードやトークンは**動的に生成する**ものなので、固定値を seeds.rb に書くとセキュリティリスクになります。そのため、**雛形をコメントアウト**して残しているだけです。実際に開発・テストで必要になったら、コメントを外して使います。

## まとめ

| 分類 | 内容 |
|---|---|
| **大きな共通点** | `ActiveRecord::Migration` を継承した `change` メソッドの中で、`create_table` → カラム定義 → `timestamps` → `add_index` という流れで書く |
| **テーブル間の共通点** | `user_id`/`client_id` は string + 必須、トークン系は重複禁止、すべて `timestamps` あり |
| **authorization_codes の独自点** | `used` フラグ、`redirect_uri`、複合インデックス `[client_id, used]` |
| **access_tokens の独自点** | `expires_at` は必須、複合インデックス `[user_id, :client_id]` |
| **refresh_tokens の独自点** | `expires_at` は NULL 許可（将来の柔軟性のため） |
| **consents の独自点** | `scope` は必須、複合ユニーク `[user_id, client_id]` |

この構造を頭に入れておけば、「なぜこのカラムが必要なのか」「このインデックスは何のためか」が、ファイルを開くたびにすぐに理解できるようになります。
