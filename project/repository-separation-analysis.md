# リポジトリ分割分析：モノレポ vs マルチレポ

## 結論

**現状の規模・チーム構成では「モノレポ（現状維持）」が有利**。リポジトリ分割は Phase 4〜5 で「サービスが別チームに移管される」か「CI/CD・監査要件が厳しくなる」までは不要です。

---

## 前提：現状の構成

現在の `phase1-feature-branches.md` では、以下のサービスを**同一リポジトリ内の独立ディレクトリ**として構成しています。

| ディレクトリ | サービス | ポート |
|---|---|---|
| `idp-auth/` | 認可サービス | 3000 |
| `idp-user/` | ユーザー管理サービス | 3001 |
| `idp-client/` | クライアント管理サービス | 3002 |
| `frontend/` | フロントエンドSPA | 5173 |
| `demo-rp/` | デモ用Relying Party | 5174 |

これを別リポジトリに分割した場合の影響を以下に示します。

---

## リポジトリ分割のメリット

| 観点 | 効果 |
|---|---|
| **独立したデプロイ・CI** | `idp-auth` の修正が `idp-user` のパイプラインを誤って実行しない |
| **権限管理** | 外部委託先に `idp-client` だけ見せる、等の細かいアクセス制御が可能 |
| **リポジトリサイズ** | 1リポジトリの肥大化を防げる（ただし現状は5ディレクトリで小規模） |
| **技術スタックの分離** | 将来的に `idp-auth` だけ Go に移行、等の自由度が上がる |

---

## リポジトリ分割のデメリット

| 観点 | 現プロジェクトへの影響 |
|---|---|
| **ローカル開発の複雑化** | 現状は `docker compose up` 1発。分割後は `git clone` × 複数 + `compose.yml` の共有方法を考える必要あり |
| **共通設定の重複・同期コスト** | RuboCop、ESLint、`.env.example`、PostgreSQL init スクリプトなどを複数リポにまたがって管理する必要が出る |
| **内部API連携のテストが困難** | `idp-auth` → `idp-user` の呼び出し統合テストを、マルチレポで実行するには Git サブモジュール or 外部スクリプトが必要 |
| **ブランチ間の整合性** | `feature/idp-auth-service` が `idp-user` の新APIに依存する場合、両リポのブランチを同期してマージしないと壊れる |
| **Phase 1〜3 の開発速度低下** | 現状は1つのPRで `frontend` + `idp-auth` + `idp-user` を横断変更できる。分割後はPRが分割され、レビュー・マージの往復が増える |

---

## 判断基準：分割を検討するタイミング

以下のいずれかが発生した場合にリポジトリ分割を検討してください。

1. **チーム分離**: `idp-auth` チームと `idp-user` チームが別になり、互いのリリースサイクルが独立する
2. **外部公開・委託**: `demo-rp` を外部開発者に公開するが、コアサービスは隠したい
3. **CI 実行時間のボトルネック**: モノレポで `bundle install` × 3 + `npm install` × 2 が並列化しても CI が5分を超える

現状（Phase 1、小規模チーム、docker compose 一括起動）ではこれらに該当しません。

---

## 推奨アクション

- **現時点**: モノレポを維持する
- **CI 設定**: `.github/workflows/` でサービスごとにジョブを分離し、変更のあったサービスのみテスト・ビルドを実行する
- **将来の分割時**: Phase 4〜5の「フロントエンド分離」や「監査・セキュリティ要件の厳格化」を契機に再検討する
