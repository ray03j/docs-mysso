## 概要比較

| 項目 | モノリス | モジュラーモノリス | マイクロサービス |
|---|---|---|---|
| **実行単位** | 単一プロセス | 単一プロセス（論理的に分割） | 複数プロセス（独立デプロイ） |
| **通信レイヤー** | プロセス内 | プロセス内（境界意識あり） | ネットワーク越し（IPC） |
| **レイテンシ** | 最低（ナノ〜マイクロ秒） | 低（ナノ〜マイクロ秒） | 高（ミリ秒〜秒） |
| **失敗モード** | 同一プロセス内でのみ考慮 | 同一プロセス内だがモジュール分離を意識 | ネワーク分断・サービス停止を前提 |
| **主な通信手段** | 関数呼び出し、共有メモリ | 公開API、DI、インメモリイベント | HTTP/gRPC、メッセージキュー、イベントストリーム |
| **通信の信頼性** | 非常に高い（同一プロセス） | 非常に高い（同一プロセス） | 低い（ネットワーク障害を前提） |
| **結合度** | 高い（密結合になりがち） | 中（明示的なインターフェースで制御） | 低い（ネットワーク境界で強制） |
| **スケーリング単位** | アプリ全体 | アプリ全体（論理的にはモジュール単位で分離） | サービス単位 |
| **技術スタックの柔軟性** | 低い（同一言語/フレームワーク） | 低い（単一デプロイ単位） | 高い（サービスごとに選べる） |
| **代表的な課題** | コードの複雑化、デプロイリスク | モジュール境界の逸脱（密結合に戻る） | 分散システムの複雑性、Observability |

## 通信方式のメリット・デメリット要約

### モノリス

| 方式 | メリット | デメリット |
|---|---|---|
| **メソッド/関数呼び出し** | 呼び出しコストがほぼゼロ<br>型安全でIDE補完が効きやすい<br>同一DB接続内でトランザクション管理が完結しやすい | 密結合になり、変更の影響範囲が広い<br>内部実装が露出しやすい<br>スレッドブロッキングの連鎖で障害範囲が広がる |
| **共有メモリ** | データコピー不要でオーバーヘッドが極めて小さい<br>追加ライブラリやインフラが不要 | 排他制御（ロック）が必要で実装が複雑<br>デッドロックやレースコンディションのリスクが高い<br>マイクロサービス化時に完全書き換えが必要 |
| **インメモリイベントバス** | 発信側と受信側が疎結合<br>ネットワーク遅延やシリアライズコストがない | 処理順序や失敗時の動作を自前で管理する必要がある<br>ハンドラの例外が発信元に影響しやすい<br>デバッグが困難 |
| **グローバル状態/シングルトン** | どこからでも即座にアクセスでき、実装コストが最小 | テストが極めて困難（モック化しにくい）<br>並行アクセス時の競合リスクが高い<br>予期しない副作用を生みやすい |

### モジュラーモノリス

| 方式 | メリット | デメリット |
|---|---|---|
| **公開API経由のメソッド呼び出し** | モジュール内部の変更が公開APIを保つ限り他モジュールに影響しない<br>コードレビューで境界違反を検出しやすい | インターフェース設計に初期コストがかかる<br>プロセス内通信ながら記述量が増える |
| **依存性注入（DI）** | テスト時にモックを注入でき、ユニットテストが容易<br>依存関係がコンストラクタで明示的になる | DIコンテナの導入・学習コスト<br>過度な抽象化で可読性が低下する |
| **ドメインイベント（インメモリ）** | モジュール間が完全に疎結合<br>将来メッセージブローカーへの移行が容易 | リトライや冪等性の担保がインメモリでは困難<br>ハンドラの例外が発信元トランザクションを失敗させる |
| **トランザクショナルアウトボックス** | DB更新とイベント発行を同一トランザクションで担保できる<br>マイクロサービス化への移行パスになる | ポーラーによる配信遅延で即時性が失われる<br>アウトボックステーブルの管理（削除、重複防止）が必要 |

### マイクロサービス

#### 同期通信

| 方式 | メリット | デメリット |
|---|---|---|
| **HTTP/REST** | 人間が読みやすく、ブラウザ/curlでデバッグ容易<br>言語非依存で最も汎用的<br>キャッシュや認証のエコシステムが豊富 | JSONのテキストシリアライズにCPUコスト<br>HTTP/1.1では高頻度通信でオーバーヘッドが大きい<br>インターフェースの型安全性がない |
| **gRPC** | HTTP/2 + バイナリでJSONより高速・ペイロード小さい<br>`.proto` で型安全なコードを自動生成<br>双方向ストリーミング対応 | ブラウザから直接呼び出せない（gRPC-Webやゲートウェイが必要）<br>人間による直接デバッグが困難<br>HTTP/2長期コネクションのLB考慮が必要 |
| **GraphQL** | クライアントが必要な構造だけ取得でき、オーバーフェッチ/アンダーフェッチを防止<br>複数リソースを1リクエストで集約できる | クエリ複雑度に応じてサーバ負荷が急増（N+1問題）<br>キャッシュ戦略がRESTより複雑<br>学習コストとスキーマ設計の初期工数が高い |
| **OpenAPI / Swagger** | API仕様の標準化<br>クライアント/サーバコードの自動生成が可能 | 仕様記述に工数がかかる<br>過度に厳密なスキーマは柔軟性を損なう |

#### 非同期通信

| 方式 | メリット | デメリット |
|---|---|---|
| **メッセージキュー** | 受信側停止時もメッセージが失われない<br>送信側は即座に応答でき、スループットが向上<br>1メッセージが1受信者に確実に届く | 即時性が失われ、リアルタイム更新には向かない<br>順序保証や重複排除を考慮する必要がある<br>ブローカーの運用・監視コストがかかる |
| **イベントストリーミング** | 過去イベントの巻き戻し再処理が可能<br>複数の独立した消費者グループが並列購読できる<br>高いスループットと耐久性 | 1メッセージが複数消費者に届くため、冪等性設計が必須<br>運用が複雑（パーティション、レプリケーション）<br>消費者遅延（Lag）の監視・スケールが必要 |
| **Pub/Sub** | 送信側は受信者を意識せず完全に疎結合<br>マネージドサービスで運用負荷が大幅に減る<br>動的に購読者を追加・削除でき、スケーリングが柔軟 | 順序保証が難しい<br>冪等性設計が必須<br>メッセージ保持期間やデッドレターキューの管理が必要 |

#### 基盤技術

| 方式 | メリット | デメリット |
|---|---|---|
| **サービスメッシュ** | アプリケーションコードを変更せずにmTLS、認証、レート制限、トレースを追加できる<br>言語やフレームワークに依存しない<br>カナリアリリースやA/Bテストが宣言的に設定できる | サイドカーの追加によりレイテンシとリソース消費が増える<br>ネットワークトポロジーが複雑化し、トラブルシューティングが困難になる<br>学習コストと運用コストが高い |
| **APIゲートウェイ** | クライアントが各サービスエンドポイントを直接知る必要がなく、入口が一元化できる<br>認証やレート制限などの横断的関心事をアプリから分離<br>プロトコル変換（REST ↔ gRPC）を吸収できる | 単一障害点（SPOF）になりうるため可用性設計が必要<br>全通信が経由するためボトルネックになりやすい<br>ルーティング設定の管理工数が増える |
| **サーキットブレイカー** | 下流サービスの障害が連鎖的に上流に波及するのを防ぐ<br>一時的な過負荷からの自動回復が期待できる | 失敗率閾値や待機時間のチューニングが難しい<br>フォールバック（代替処理）の設計に工数がかかる<br>分散システムの動作を直感的に把握しにくくなる |
| **分散トレーシング** | 複数サービスにまたがるリクエストの流れを可視化し、ボトルネックの特定が容易<br>ログだけでは分からない「どのサービス間で時間がかかっているか」を把握できる | スパン情報の収集・保存にリソースを消費<br>すべてのサービスに計装（Instrumentation）を導入する工数がかかる<br>トレースIDの伝播忘れや中断で途切れたトレースが生じやすい |

## 通信方式の適用シーン・具体例

### モノリス

| シーン | 推奨方式 | 具体例 |
|---|---|---|
| 同一ドメイン内の業務処理 | メソッド/関数呼び出し | 注文処理から在庫確認を同期的に呼び出す |
| 高頻度なデータ共有 | 共有メモリ | リアルタイムレート制限カウンター、キャッシュ |
| 同一トランザクション内の副作用通知 | インメモリイベントバス | 注文確定後のメール送信、ログ記録 |
| グローバル設定・共通コンテキスト | 依存性注入（DI） | DB接続、設定値、リクエストコンテキストの注入 |

### モジュラーモノリス

| シーン | 推奨方式 | 具体例 |
|---|---|---|
| モジュール間の業務連携 | 公開API経由のメソッド呼び出し | 注文モジュールから会員モジュールの会員情報を取得 |
| テスト容易性を重視した設計 | 依存性注入（DI） | リポジトリインターフェースを定義し、テスト時にインメモリ実装を注入 |
| 最終的な一貫性が許容される連携 | ドメインイベント（インメモリ） | 注文確定イベント→在庫モジュールへ在庫引当処理を非同期で実行 |
| Exactly Once 配信が必要な連携 | トランザクショナルアウトボックス | DB更新と「配送依頼イベント」の発行を同一トランザクションで担保 |

### マイクロサービス

| シーン | 推奨方式 | 具体例 |
|---|---|---|
| クライアントからの直接的な操作 | HTTP/REST | フロントエンドからの CRUD API 呼び出し |
| 内部サービス間の高頻度通信 | gRPC | 商品サービス→在庫サービスの在庫確認 |
| 複数リソースを集約するクエリ | GraphQL | ユーザープロフィール＋注文履歴＋おすすめ商品を1リクエストで取得 |
| 非同期処理、作業キュー | メッセージキュー | 画像アップロード後のリサイズ処理、メール送信キュー |
| イベントの複数購読、巻き戻し | イベントストリーミング | 注文イベントをAnalytics、監査、推薦エンジンが独立して購読 |
| 軽量な通知・ブロードキャスト | Pub/Sub | 在庫変更のリアルタイム通知 |
| 認証・レート制限・ルーティング | APIゲートウェイ | 全クライアントリクエストの入口でJWT検証 |
| サービス間通信の保護・監視 | サービスメッシュ | mTLS 自動化、サービス間の分散トレーシング |

## ハイブリッド構成パターン

実際のシステムでは、単一のアーキテクチャだけでなく複数を組み合わせることが多い。

| パターン | 構成 | 適用シーン |
|---|---|---|
| **モジュラーモノリス + 一部マイクロサービス** | コアドメインはモジュラーモノリス、高負荷・特化処理だけを切り出し | 大半の業務はシンプルに、画像処理やAI推論だけスケールしたい |
| **モノリス + イベントストリーミング** | 単一アプリだが、外部連携や集計はKafka等で非同期化 | リアルタイム集計や外部SaaS連携が必要だが、内部はシンプルに保ちたい |
| **マイクロサービス + モジュラーモノリス（ストラングラーフィグ）** | レガシーモノリスを段階的にマイクロサービス化 | リスクを抑えながら既存システムを分割していく |
| **BFF（Backend for Frontend）+ マイクロサービス** | クライアント毎にAPI集約層を設け、下位はgRPC/REST | Web、モバイル、パートナーAPI それぞれに最適な応答を返したい |
| **CQRS + イベントソーシング** | コマンド（書き込み）とクエリ（読み込み）を分離、イベントストリームをソース・オブ・トゥルースに | 高頻度な読み込みと複雑なドメイン変更を同時にスケールさせたい |

## 選定の判断基準

```
1. 同一プロセス/同一DB内か？
   ├─ Yes → モノリス/モジュラーモノリス（関数呼び出し or 公開API）
   └─ No  → 2へ

2. 即時の応答が必要か？
   ├─ Yes → 同期通信（HTTP/REST or gRPC）
   └─ No  → 3へ

3. 1メッセージが1受信者か？
   ├─ Yes → メッセージキュー（RabbitMQ, SQS等）
   └─ No  → イベントストリーミング or Pub/Sub（Kafka, Pub/Sub等）

4. クライアントが必要なデータだけ取得したいか？
   ├─ Yes → GraphQL
   └─ No  → REST or gRPC

5. 型安全性・パフォーマンスが最重要か？
   ├─ Yes → gRPC
   └─ No  → REST
```

## よくある組み合わせ例

| 構成要素 | 使い分け |
|---|---|
| **フロントエンド → BFF** | HTTP/REST または GraphQL（人間が読みやすく、ブラウザから直接呼び出せる） |
| **BFF → 内部サービス** | gRPC（型安全・高速・サーバー間通信） |
| **サービス間の非同期連携** | メッセージキュー or イベントストリーミング（可用性・耐久性） |
| **認証・認可（SSO）** | OpenID Connect（ID Token でのユーザー属性伝達） + OAuth 2.0（アクセストークンでの API 保護） |
| **外部SaaS連携** | Webhook + メッセージキュー（受信後の信頼性担保） |

## 選定の指針

- **モノリス**: 小〜中規模。チームが少ない。初期開発速度を重視。デプロイ頻度が低く、ドメイン境界がまだ不安定。
- **モジュラーモノリス**: 中規模。ドメインモデルが複雑だが、まだ分散のコストを払う必要がない。将来的な分割を見越してモジュール境界を整備したい。1日数回のデプロイで十分。
- **マイクロサービス**: 大規模。複数チームが並行開発。サービスごとに異なる技術スタックやスケーリング要件がある。分散システムの運用能力がある。独立デプロイが必須。
