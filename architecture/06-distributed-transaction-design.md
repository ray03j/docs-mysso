# 分散トランザクション設計メモ

本ドキュメントは、マイクロサービス間でトランザクション整合性を保つ設計について、本プロジェクトのコンテキストに沿ってまとめたものです。

---

## 1. 分散トランザクションとは

複数の独立したサービス・データベースにまたがる一連の処理を、**すべて成功するか、すべて失敗するか**の整合性を保つための設計・手法の総称です。

モノリシックアプリケーションでは1つのDBトランザクションで保証できていたものが、マイクロサービス化によりネットワーク越しの複数DB操作になるため、新たな整合性保証の仕組みが必要になります。

---

## 2. 本プロジェクトで発生するシナリオ

認証（`idp-user`）と認可（`idp-auth`）を**厳密に分離**する場合、ログイン処理で以下の2つのDB更新が発生します。

| サービス | DB操作 | 内容 |
|---|---|---|
| `idp-user` | INSERT/UPDATE | 認証成功履歴、最終ログイン日時 |
| `idp-auth` | INSERT | 認可コード（Authorization Code）の生成・保存 |

これらは**別サービス・別DB**なので、単一トランザクションでは保証できません。

```
[RP] → [idp-auth] ──HTTP──→ [idp-user]
            │                     │
            ▼                     ▼
      認可コードをDBに保存    認証履歴をDBに保存
            │                     │
            └─── 整合性を保つ必要 ───┘
```

---

## 3. 代表的な実現パターン

### 3.1 2PC（Two-Phase Commit）

 coordinator が各参加者に「準備できるか」を問い合わせ（Phase 1）、全員OKならコミットを指示する（Phase 2）。

- **メリット**：強い整合性（ACIDに近い）
- **デメリット**： coordinator がSPOFになる。ロック保持時間が長くなり、パフォーマンス・可用性が低下。
- **向き先**：金融系等、強整合性が絶対条件のシステム

### 3.2 Sagaパターン

各サービスが独立したローカルトランザクションを順次実行し、失敗時は**補償トランザクション（Compensating Transaction）**を実行してロールバック相当を実現する。

```
成功時: T1 → T2 → T3 → ... → 完了
失敗時: T1 → T2 → (T3失敗) → C2 → C1 → 取消
```

- **メリット**：2PCより可用性が高い。各サービスが独立して動作できる。
- **デメリット**：最終的整合性（Eventual Consistency）。補償設計の工数が大きい。一時的な不整合が許容できる必要がある。
- **向き先**：一般的なマイクロサービス（本プロジェクトの将来形）

### 3.3 イベントソーシング + CQRS

DBに状態を直接保存するのではなく、すべての変更をイベントとして記録（イベントストア）。各サービスがイベントを購読して自身のDBを更新する。

- **メリット**：完全な履歴が残る。イベントの再再生が可能。
- **デメリット**：学習コスト・実装コストが高い。既存ORMとの相性が悪いことも。

### 3.4 Outboxパターン

DB更新とメッセージ発行を同一トランザクションで行い、別プロセスがOutboxテーブルをポーリングしてメッセージブローカーに転送する。

- **メリット**：「DB更新は成功したがイベント発行が失敗した」という不整合を防げる。
- **デメリット**：ポーリング機構の実装が必要。即時性が若干犠牲になる。

---

## 4. 本プロジェクトでの選定

### 結論：当面は分散トランザクションを**導入しない**

`domain-boundary-design.md` の **案B（実用的緩和）** を採用し、以下の設計で回避します。

```
[idp-auth] ──HTTP同期呼び出し──→ [idp-user]
     │
     ▼
認可コード発行・保存を同一サービス内で完結
```

### 案Bで分散トランザクションが不要な理由

案B（実用的緩和）では、ログイン処理における整合性保証が単一サービス内で完結するため、分散トランザクションの機構が不要になります。

| 案A（厳密分離） | 案B（実用的緩和） |
|---|---|
| `idp-user` で認証履歴を更新し、`idp-auth` で認可コードを保存する。**2つのDB更新が別サービスにまたがる**。 | `idp-auth` が `idp-user` に**認証を問い合わせるだけ**（確認・照会）。認可コードの生成・保存は `idp-auth` の**単一DB内で完結**する。 |
| 両方のDB更新を「すべて成功またはすべて失敗」に保つ必要があるため、分散トランザクションが必須。 | `idp-user` 側の認証履歴更新は、認可コード発行とは**独立した副作用**。即時整合性が保証できなくてもOAuthフロー全体に影響しない。 |

つまり、案Bでは「複数のDBを跨ぐ更新を同一トランザクションで縛る」という前提自体が消えるため、2PCやSagaといった分散トランザクション機構の導入コストを回避できます。

### 判断根拠

| 観点 | 理由 |
|---|---|
| **規模** | RP数2〜3個、個人開発レベル。整合性が崩壊しても影響範囲が限定的 |
| **工数** | Sagaの補償設計やOutboxのポーリング機構は、学習・実装・デバッグ工数が大きい |
| **段階的進化** | まず動くものを作り、分散トランザクションは将来の課題として棚上げする |
| **代替学習** | ドメイン分離の学習価値は、非同期の監査ログ（`idp-audit`）で補える |

### ただし守るべき設計

分散トランザクションを導入しないからと言って、以下は守ります。

1. **冪等性設計**：認証APIの呼び出しが重複しても安全なようにする
2. **明確な責務分離**：`idp-auth` はパスワード知識を持たず、`idp-user` は認可コード知識を持たない
3. **イベント非同期化の準備**：監査ログはRedis Pub/Subで疎結合にして、将来のイベント駆動設計の足がかりとする

---

## 5. 将来の移行パス

ユーザー規模・RP数が増え、認証と認可の厳密分離（案A）が必要になった場合：

```
Phase 1（現在）: HTTP同期呼び出しで回避
        ↓
Phase 2: Sagaパターン導入（Orchestration型）
        ↓
Phase 3: Outboxパターン + メッセージブローカー導入
```

移行時の判断材料：
- 認証APIのレイテンシがボトルネックになったか
- 認可コード発行の失敗率が許容できない水準に達したか
- 複数人開発になり、サービス間の責務を厳密に分ける必要が出たか
