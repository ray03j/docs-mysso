## 1. 分散トランザクションとは

複数の独立したサービス・データベースにまたがる一連の処理を、**すべて成功するか、すべて失敗するか**の整合性を保つための設計・手法の総称です。

モノリシックアプリケーションでは1つのDBトランザクションで保証できていたものが、マイクロサービス化によりネットワーク越しの複数DB操作になるため、新たな整合性保証の仕組みが必要になります。

---

## 2. 分散トランザクションの設計観点

分散トランザクションの本質的な難しさは、「**ネットワーク越しに複数の独立したシステムを一貫性を保ちながら協調させる**」ことです。以下の6観点を押さえておく必要があります。

### 2.1 整合性の担保

分散環境では厳密なACIDを保つと性能・可用性が犠牲になる。業務要件に応じて整合性レベルを選定する。

| 整合性レベル | 特徴 | トレードオフ |
|---|---|---|
| **強整合性** | 常に最新データが読める | 可用性・レイテンシが犠牲になる |
| **最終的整合性** | 一時的な不整合を許容し、最終的に収束 | 可用性・性能は高いが、一時的な古い値が読める |
| **因果整合性** | 因果関係のある操作だけ順序を保証 | 中間的。実装が比較的容易 |

認可コードの発行のようなクリティカルな処理は強整合性が求められるが、認証履歴の更新のような副次的処理は最終的整合性で十分です。

**本プロジェクトでは**、案Bの単一サービス完結によりDBトランザクションで強整合性を担保。認証履歴の更新は別途非同期で行い、最終的整合性とする。

### 2.2 ネットワーク障害への対処

分散環境ではネットワーク障害は前提。メッセージの消失や遅延により「送ったが届かない」「応答が来ない」といった曖昧な状態が生じる。

| 障害パターン | 対処法 | 注意点 |
|---|---|---|
| **メッセージ消失** | 再試行（Retry） | 冪等性がないと二重更新のリスク |
| **応答遅延** | タイムアウト + サーキットブレーカー | 誤ったタイムアウト判定で不整合が生じる |
| **ネットワーク分割** | 分割耐性を意識した設計（CAP） | CPかAPかの自覚的な選択が必要 |

再試行だけでは重複更新のリスクがあるため、冪等性キー（Idempotency Key）の付与が必須です。

**本プロジェクトでは**、HTTP同期呼び出しにタイムアウト設定を行い、認証APIには冪等性を確保する。

### 2.3 合意形成（Consensus）

**複数ノードで同じ結果に合意する仕組み**です。ネットワーク障害やノードクラッシュが起きても、全員が「コミット」または「アボート」のどちらかに納得できる必要があります。

| プロトコル | 特徴 | トレードオフ |
|---|---|---|
| **2PC** | Coordinatorが全員の承認を取ってからコミット指示 | 整合性は強いが、Coordinator障害時にブロッキング（可用性低下） |
| **3PC** | 2PCにPre-commitを追加しブロッキングを緩和 | ネットワーク分割時に安全性が損なわれるリスク |
| **Paxos** | 過半数の合意で決定。非同期環境でも耐障害性あり | 実装が極めて複雑 |
| **Raft** | Paxosを構造化（リーダー選出＋ログ複製） | etcd, Consulで採用。実装例が豊富で理解しやすい |

合意形成プロトコルは整合性を優先する「CP」系です。一方、Sagaパターンは可用性を優先する「AP」系で、事後的に補償で整合性を取り戻します。分散トランザクションを設計する際は、このトレードオフを意識して選択します。

**本プロジェクトでは現時点で不要**です（案Bで単一サービス内完結）。ただし、将来の厳密分離（案A）に移行する際は、マイクロサービス間で2PCを自前実装するよりSagaパターンによる緩和が現実的です。

### 2.4 性能とスケーラビリティ

分散トランザクションはロック保持や調整コミュニケーションが増え、レイテンシが大きくなる。スケールを維持するには、ロックの範囲を最小化し、非同期化を進める。

| アプローチ | 性能特性 | トレードオフ |
|---|---|---|
| **2PC** | ロック保持時間が長く、スループットが低下 | 強整合性は保てるが、ボトルネックになりやすい |
| **Saga** | 非同期実行でスループット向上 | 補償処理の設計・運用工数が増える |
| **最終的整合性** | 即時整合性を諦め、可用性・性能を確保 | 一時的な不整合を許容する必要がある |

分散ロックはなるべく避け、メッセージキューによる非同期化でスケールする設計が基本です。

**本プロジェクトでは**、単一サービス完結により分散ロックは不要。将来のイベント駆動化で非同期化を進める予定。

### 2.5 部分的失敗と回復

複数サービスのうち一部だけ成功し、残りが失敗する「部分的失敗」への対処が必須。コミット前か後かで回復策が異なる。

| 失敗フェーズ | 状態 | 回復策 |
|---|---|---|
| **事前失敗**（Commit前） | 全サービス未コミット | ロールバックまたはアボート |
| **事後失敗**（Commit後） | 一部コミット済み | 補償トランザクション（Saga）で取消 |
| **状態不明** | 成功か失敗か判断できない | 冪等な問い合わせで状態確認し、再試行 |

冪等性設計がないと、状態不明からの再試行で二重更新が発生するリスクがあります。

**本プロジェクトでは**、単一サービス完結により部分的失敗はDBレイヤのロールバックで解決。APIは冪等性を確保して、将来の分散化に備える。

### 2.6 監視とデバッグ

分散システムではログが各サービスに分散しており、原因特定が極めて困難。可観測性（Observability）の基盤がないと運用が成り立ちません。

| 可観測性の柱 | 役割 | 具体例 |
|---|---|---|
| **メトリクス** | 数値化された状態を監視 | レイテンシ、エラー率、スループット |
| **ログ** | 構造化ログで横断検索 | JSON形式のログを集中管理（ELK等） |
| **トレース** | リクエストの流れを追跡 | Trace IDを各サービスで引き継ぎ可視化 |

分散トレーシングがないと、どのサービスで時間がかかっているか、どこでエラーが発生したかを把握できません。

**本プロジェクトでは**、現状は2サービスのみだが、Trace IDの付与と構造化ログのフォーマットを最初から決めておき、将来の分散化に備える。

## 3. 本プロジェクトで発生するシナリオ

認証（`idp-user`）と認可（`idp-auth`）を**厳密に分離**する場合、ログイン処理で以下の2つのDB更新が発生します。

| サービス | DB操作 | 内容 |
|---|---|---|
| `idp-user` | INSERT/UPDATE | 認証成功履歴、最終ログイン日時 |
| `idp-auth` | INSERT | 認可コード（Authorization Code）の生成・保存 |

これらは**別サービス・別DB**なので、単一トランザクションでは保証できません。

```
[RP] → [idp-auth] ──HTTP──→ [idp-user]
            │                     │
            ▼                     ▼
      認可コードをDBに保存    認証履歴をDBに保存
            │                     │
            └─── 整合性を保つ必要 ───┘
```

## 4. 代表的な実現パターン

### 4.1 2PC（Two-Phase Commit）

 coordinator が各参加者に「準備できるか」を問い合わせ（Phase 1）、全員OKならコミットを指示する（Phase 2）。

- **メリット**：強い整合性（ACIDに近い）
- **デメリット**： coordinator がSPOFになる。ロック保持時間が長くなり、パフォーマンス・可用性が低下。
- **向き先**：金融系等、強整合性が絶対条件のシステム

### 4.2 Sagaパターン

各サービスが独立したローカルトランザクションを順次実行し、失敗時は**補償トランザクション（Compensating Transaction）**を実行してロールバック相当を実現する。

```
成功時: T1 → T2 → T3 → ... → 完了
失敗時: T1 → T2 → (T3失敗) → C2 → C1 → 取消
```

- **メリット**：2PCより可用性が高い。各サービスが独立して動作できる。
- **デメリット**：最終的整合性（Eventual Consistency）。補償設計の工数が大きい。一時的な不整合が許容できる必要がある。
- **向き先**：一般的なマイクロサービス（本プロジェクトの将来形）

### 4.3 イベントソーシング + CQRS

DBに状態を直接保存するのではなく、すべての変更をイベントとして記録（イベントストア）。各サービスがイベントを購読して自身のDBを更新する。

- **メリット**：完全な履歴が残る。イベントの再再生が可能。
- **デメリット**：学習コスト・実装コストが高い。既存ORMとの相性が悪いことも。

### 4.4 Outboxパターン

DB更新とメッセージ発行を同一トランザクションで行い、別プロセスがOutboxテーブルをポーリングしてメッセージブローカーに転送する。

- **メリット**：「DB更新は成功したがイベント発行が失敗した」という不整合を防げる。
- **デメリット**：ポーリング機構の実装が必要。即時性が若干犠牲になる。

## 5. 本プロジェクトでの選定

### 結論：当面は分散トランザクションを**導入しない**

`domain-boundary-design.md` の **案B（実用的緩和）** を採用し、以下の設計で回避します。

```
[idp-auth] ──HTTP同期呼び出し──→ [idp-user]
     │
     ▼
認可コード発行・保存を同一サービス内で完結
```

### 案Bで分散トランザクションが不要な理由

案B（実用的緩和）では、ログイン処理における整合性保証が単一サービス内で完結するため、分散トランザクションの機構が不要になります。

| 案A（厳密分離） | 案B（実用的緩和） |
|---|---|
| `idp-user` で認証履歴を更新し、`idp-auth` で認可コードを保存する。**2つのDB更新が別サービスにまたがる**。 | `idp-auth` が `idp-user` に**認証を問い合わせるだけ**（確認・照会）。認可コードの生成・保存は `idp-auth` の**単一DB内で完結**する。 |
| 両方のDB更新を「すべて成功またはすべて失敗」に保つ必要があるため、分散トランザクションが必須。 | `idp-user` 側の認証履歴更新は、認可コード発行とは**独立した副作用**。即時整合性が保証できなくてもOAuthフロー全体に影響しない。 |

つまり、案Bでは「複数のDBを跨ぐ更新を同一トランザクションで縛る」という前提自体が消えるため、2PCやSagaといった分散トランザクション機構の導入コストを回避できます。

### 判断根拠

| 観点 | 理由 |
|---|---|
| **規模** | RP数2〜3個、個人開発レベル。整合性が崩壊しても影響範囲が限定的 |
| **工数** | Sagaの補償設計やOutboxのポーリング機構は、学習・実装・デバッグ工数が大きい |
| **段階的進化** | まず動くものを作り、分散トランザクションは将来の課題として棚上げする |
| **代替学習** | ドメイン分離の学習価値は、非同期の監査ログ（`idp-audit`）で補える |

### ただし守るべき設計

分散トランザクションを導入しないからと言って、以下は守ります。

1. **冪等性設計**：認証APIの呼び出しが重複しても安全なようにする
2. **明確な責務分離**：`idp-auth` はパスワード知識を持たず、`idp-user` は認可コード知識を持たない
3. **イベント非同期化の準備**：監査ログはRedis Pub/Subで疎結合にして、将来のイベント駆動設計の足がかりとする

## 6. 将来の移行パス

ユーザー規模・RP数が増え、認証と認可の厳密分離（案A）が必要になった場合：

```
Phase 1（現在）: HTTP同期呼び出しで回避
        ↓
Phase 2: Sagaパターン導入（Orchestration型）
        ↓
Phase 3: Outboxパターン + メッセージブローカー導入
```

移行時の判断材料：
- 認証APIのレイテンシがボトルネックになったか
- 認可コード発行の失敗率が許容できない水準に達したか
- 複数人開発になり、サービス間の責務を厳密に分ける必要が出たか
